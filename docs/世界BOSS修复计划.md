# 世界 BOSS 修复计划

## 1. 目标与范围

本计划用于修复当前世界 BOSS 的活动、战斗、奖励和生命周期断链，并把等级、刷新和房间选择规则收敛为可验证的单一流程。

本次范围包括：

- 世界 BOSS 系统任务的刷新、停止和热更新生命周期；
- 在线玩家分组、活动可见性、传送和攻击资格；
- BOSS 死亡、伤害资格、尸体领取、自动拾取和活动面板快捷领取；
- 每日领取次数、领取幂等、活动过期和旧事件清理；
- 随机房间筛选、刷新时间配置、运行日志和专项测试。

本次不顺带调整普通 NPC、襄阳守城和门派战的奖励数值。若需要修改核心伤害记录，应先确认不会改变这些系统的既有结算结果。

## 2. 当前代码基线

| 环节 | 当前实现 | 当前问题 |
| --- | --- | --- |
| 定时刷新 | `server/res/task/boss_task.ts` 自行计算下一次时间 | 21 点密集刷新，其他时段每小时随机刷新；规则未配置化，存在无效字段 |

| 出生房间 | `ROOM.RANDOM()` | 只按容量粗筛，可能进入禁战或不适合群战的房间 |

| 自动拾取 | `WORLD.auto_get` 遍历死亡房间玩家 | 与手动尸体领取走同一生成入口，但没有统一的领取状态事务 |

当前关键调用链：

```text
BossTask.run()
    → check_users()
    → create_boss()
    → ROOM.RANDOM()
    → EVENTS.add(挑战活动)

NPC.die()
    → BossTask.on_died()（this 为 BOSS NPC）
    → 尸体注入 query_items / clear_items
    → EVENTS.add(领取活动)
    → WORLD.auto_get()
```

## 3. 修复后的目标行为

### 3.1 BOSS 与活动槽生命周期

每只 BOSS 必须具有唯一的运行批次和明确状态；活动槽本身不随 BOSS 死亡删除，而是持续存在 24 小时：

```text
scheduled → active → defeated → quick-claimable → replaced/cleaned
                  ↘ aborted → cleaned
```

- `active`：BOSS 存活，活动按钮为“前往挑战”；
- `defeated`：死亡回调冻结伤害快照，不再接受新的伤害变更；
- `quick-claimable`：当前没有 BOSS，活动按钮为“快速完成”；只有该玩家对上一个 BOSS 的输出达到 10% 才可快速完成；
- `replaced`：下一只同等级 BOSS 出现，活动按钮切换回“前往挑战”，上一个 BOSS 的快速完成入口关闭；
- `aborted`：任务停止、热更新或创建失败时执行幂等清理；
- 活动槽 24 小时常驻，不因 BOSS 死亡立即删除，也不使用“领取截止时间”提前隐藏活动。

任意状态下重复执行清理不得重复销毁对象、重复通知或抛出异常。

### 3.2 等级与参与资格

等级分桶、活动可见性、传送资格、攻击资格和领奖资格必须调用同一个函数，禁止分别使用 `===`、截断下标和 `on_kill` 独立推断。

建议定义：

```ts
type BossGrade = 1 | 2 | 3 | 4 | 5 | 6;

function getBossGrade(userLevel: number): BossGrade | undefined;
function canChallengeBoss(me: USER, boss: NPC): boolean;
```

当前决策：

1. 1 至 5 级规则保持现状；
2. 6 级及以上暂时继续归入 5 级组；
3. 在等级分组代码旁增加 `// FIXME: 6级武神 BOSS 待办，暂沿用5级分组`；
4. 武神 BOSS 的模板、奖励、开放条件和活动入口不在本次修复中实现，单独作为后续待办；
5. 活动、传送、攻击和领奖必须对当前“归入 5 级”的规则保持一致，不能出现收到传闻却无法参与的半参与状态。

BOSS 模板自身也必须声明所属活动等级。生成某个等级的场次时，只能从 `template.level === grade` 的模板池中随机，模板池之间不累计、不向下兼容。例如武士场次只会刷新武士模板，武帝场次绝不能抽到赵三拳、鳌拜等武士模板。

旧配置 `player_levels` 已留下模板等级线索：赵三拳、鳌拜、陈近南为 1 级武士模板，洪安通为 2 级武师模板。当前仓库尚未配置其余武师模板以及 3～5 级模板；实施时必须补齐后才能开放对应生成。某级模板池为空时，应跳过该级生成并记录配置错误，禁止回退到低级模板冒充高级 BOSS。6 级仍按既定决策只保留武神 `FIXME`。

### 3.3 奖励与每日次数

尸体、自动拾取和活动面板必须调用同一个领取服务。活动面板的“快速完成”是一次性操作，每次点击最多完成一只 BOSS：

```ts
claimBossReward(me, runtime, source)
    → 校验批次和活动当前状态
    → 校验玩家等级与伤害资格
    → 校验当日次数
    → 快速完成额外校验该玩家输出达到该 BOSS 最大气血的 10%
    → 向玩家弹出确认提示，确认后继续本次操作
    → 获取或生成该玩家的奖励快照
    → 检查背包容量，背包满时阻止领取
    → 尝试放入背包
    → 成功后提交“已领取”和每日次数
    → 返回结构化结果
```

目标约束：

- 同一玩家、同一 BOSS 批次最多成功领取一次；
- 查看尸体只展示奖励，不增加 `bcc`；
- 背包满时快速完成直接阻止领取，不弹出已完成或扣次数结果；
- 物品创建失败或发放失败时不增加 `bcc`，奖励保持可重试；
- 尸体领取成功后再点活动快速完成，应提示已经领取，不能重复发奖；
- 自动拾取和手动领取同时触发时，必须由同一领取状态保证幂等；
- 达到 1% 及以上并实际发放完整奖励时计入每日 5 次额度；低于 1% 的安慰奖不增加 `bcc`；
- 快速完成每次只处理一只 BOSS；玩家可以重复点击并逐次确认，直到达到每日上限；
- `bcc` 继续在每日 05:00 重置，与信息面板展示保持一致。

建议把动态的 `Record<string, OBJ[]>` 改为显式状态：

```ts
interface BossPlayerReward {
    state: 'eligible' | 'generated' | 'claimed';
    damage: number;
    damagePercent: number;
    items?: OBJ[];
    claimedAt?: number;
    source?: 'corpse' | 'auto' | 'event';
}
```

如果物品对象不适合跨较长时间保存在内存中，可以保存确定后的奖励描述，在真正交付时创建物品；但必须保证重试不会重新抽奖。

### 3.3.1 正常掉落组成

世界 BOSS 的完整奖励不是只有银子、玄晶和宝石。每个合格玩家的个人奖励快照应由三层组成：

1. **BOSS 模板掉落**：调用当前 BOSS 模板声明的 `drop_list`，保留赵三拳、鳌拜、陈近南、洪安通各自已有的银钱、装备、秘籍和特殊物品；
2. **世界 BOSS 基础奖励**：保留当前按伤害档位生成的安慰奖、玄晶和碎裂宝石；
3. **世界 BOSS 工具池**：按该只 BOSS 模板配置的难度档生成对应品级工具。

当前为个人掉落模型，模板掉落也必须进入该玩家的奖励快照；不能直接复用尸体上唯一一份共享 `corpse.items`，否则第一个玩家拾取后其他玩家无法获得，也无法保证尸体领取和快速完成结果一致。

正常尸体领取、自动拾取和活动快速完成必须消费同一份完整奖励快照。快速完成不能只发“基础奖励”而漏掉模板掉落或工具，也不能重新抽取一次模板掉落。

各模板现有的主要 `drop_list`：

| BOSS 模板 | 当前模板掉落 |
| --- | --- |
| 赵三拳 | 银钱、基础装备、基础武学书、流氓装备、太祖长拳秘籍等 |
| 鳌拜 | 银钱、基础装备、牢房钥匙、混元一气/飞檐走壁/伏虎拳秘籍、鳌拜装备、契约、挑战票等 |
| 陈近南 | 银钱、基础装备、云龙剑/云龙身法/云龙心法秘籍、云龙剑等 |
| 洪安通 | 银钱、基础装备、神龙教装备、神龙系武学秘籍等 |

工具池目标：

| 工具 | 资源路径 | 当前支持品级 | 说明 |
| --- | --- | ---: | --- |
| 挖矿指南 | `sp/tool/exp#<grade>` | 1～5 | 使用后临时提高全服挖矿经验效率 |
| 鱼饵 | `sp/tool/er#<grade>` | 1～5 | 单个鱼饵；如果希望一次掉落一包，应改用 `sp/tool/er2#<grade>` |
| 钓鱼竿 | `sp/tool/diao#<grade>` | 1～6 | 提高钓鱼稀有产出 |
| 藏宝箱 | 建议新增 `sp/tool/box#<grade>` | 1～5 | 绿色至橙色可开启物品，打开后从黄金、玄晶、秘籍碎片、宝石四类中随机获得一类 |
| 铁镐 | `sp/tool/chu#<grade>` | 1～6 | 提高挖矿稀有产出 |
| 药王神篇 | `sp/tool/yao#<grade>` | 1～6 | 提高采药稀有产出；6 级名称为神农百草经 |

工具的品级、具体掉落概率和每次数量需要作为 BOSS 模板难度配置的显式字段，不在领取函数里散落硬编码。藏宝箱作为新物品新增支持 `#1`～`#5` 的分级资源；是否增加第 6 品级应由未来武神难度配置决定，不能直接跟随活动等级推断。

#### 藏宝箱规格

藏宝箱是绿色、蓝色、黄色、紫色、橙色五档可直接打开的物品。`grade` 由掉落它的 BOSS 难度档决定：

| `grade` | 颜色 | 建议路径 |
| ---: | --- | --- |
| 1 | 绿色 | `sp/tool/box#1` |
| 2 | 蓝色 | `sp/tool/box#2` |
| 3 | 黄色 | `sp/tool/box#3` |
| 4 | 紫色 | `sp/tool/box#4` |
| 5 | 橙色 | `sp/tool/box#5` |

打开时只命中以下四类中的一类；默认可以等概率抽取，权重必须集中在宝箱配置中，便于后续调整：

1. 黄金；
2. 玄晶；
3. 秘籍碎片；
4. 宝石。

仓库中没有名为“秘境碎片”的物品，现有对应资源是 `book/bc#<skillId>` 的“秘籍碎片/残页”。本计划按“秘籍碎片”实现；如果产品实际指另一种秘境货币，需要另增资源并替换该分支。

建议数值表：

| 宝箱品级 | 黄金 | 玄晶（黄金数量 × 5） | 宝石/秘籍物品数 |
| ---: | ---: | ---: | ---: |
| 1 绿 | 10～50 | 50～250 | 随机 1～3 个 |
| 2 蓝 | 20～100 | 100～500 | 随机 1～3 个 |
| 3 黄 | 40～200 | 200～1000 | 随机 1～3 个 |
| 4 紫 | 60～300 | 300～1500 | 随机 1～3 个 |
| 5 橙 | 100～500 | 500～2500 | 随机 1～3 个 |

玄晶数量不是随宝箱等级按 `1～5` 倍成长，而是始终为同档黄金随机数量的 5 倍。实现时先按该品级黄金区间随机出基准数量；若抽中黄金则发基准数量，若抽中玄晶则发 `基准数量 × 5`。

宝石和秘籍碎片的数量也不随宝箱等级增加：所有品级都随机发放 `1～3` 个物品。宝箱等级只决定所发物品的品级和显示颜色。

宝石分支规则：

- 随机决定本次数量 `1～3`；
- 从红、绿、蓝、黄四系中不重复抽取对应数量，每种发放 1 块；
- 宝石物品品级等于宝箱品级；由于宝石路径参数从 `#0` 开始，实际路径参数为 `box.grade - 1`，例如绿色箱掉 `#0`、橙色箱掉 `#4`。

秘籍碎片分支规则：

- 随机决定本次数量 `1～3`；
- 从 `SKILL.query_grade() === box.grade` 的可掉落武学中不重复抽取对应数量，每种发放 1 份 `book/bc#<skillId>`；
- 必须维护明确的可掉落秘籍池，排除基础技能、知识技能、活动专属技能和未开放技能；
- 当某品级候选不足时只发实际可用种类，不跨品级补发。

### 3.3.2 BOSS 等级区分

当前代码中“等级”实际混用了多种含义，修复时必须分开命名：

| 概念 | 建议字段 | 当前来源 | 用途 |
| --- | --- | --- | --- |
| 活动等级 | `runtime.grade` / `BossGrade` | 参战玩家分组，1～5；6 级暂归 5 级 | 活动名称、参与资格、快速完成资格、选择同级模板池 |
| 模板所属等级 | `template.level` | BOSS 模板显式配置 | 决定该模板允许出现在哪个活动等级；必须与 `runtime.grade` 完全相等 |
| 模板标识 | `template.id` / `npcPath` | 赵三拳、鳌拜、陈近南、洪安通等 | 决定 NPC 模板及其原生 `drop_list` |
| 数值难度 | `template.difficulty` | 当前线索为 3、5、10、12，预留 20、40 | 计算气血、技能和额外掉率，并决定 `toolGrade` |
| 工具品级 | `template.toolGrade` | 由模板难度配置，1～5 | 决定挖矿指南、鱼饵、钓竿、藏宝箱、铁镐、药王神篇的资源品级 |

活动等级对应名称：

| `boss.level` | 活动称号 | 当前处理 |
| ---: | --- | --- |
| 1 | 武士 BOSS | 已有赵三拳、鳌拜、陈近南三个同级模板 |
| 2 | 武师 BOSS | 当前仅确认洪安通模板，模板池待补齐 |
| 3 | 宗师 BOSS | 当前缺少明确模板配置，补齐前不得用低级模板代替 |
| 4 | 武圣 BOSS | 当前缺少明确模板配置，补齐前不得用低级模板代替 |
| 5 | 武帝 BOSS | 当前缺少明确模板配置，补齐前不得用低级模板代替 |
| 6 | 武神 BOSS | `FIXME`；当前玩家暂归 5 级，不创建真正的 6 级 BOSS |

模板池必须按等级隔离：同一模板只属于一个活动等级，不允许把低级模板提升成高级场次实例。当前配置可确认的对应关系为：

| 模板 | 模板等级 | 当前难度 | 目标工具品级 |
| --- | ---: | ---: | ---: |
| 赵三拳 | 1（武士） | 3 | 1（绿） |
| 鳌拜 | 1（武士） | 5 | 2（蓝） |
| 陈近南 | 1（武士） | 10 | 3（黄） |
| 洪安通 | 2（武师） | 12 | 4（紫） |

上表的模板等级来自现有 `player_levels`，难度来自现有 `levels`；后续新增模板也必须同时填写 `level`、`difficulty` 和 `toolGrade`。首版难度到工具品级的配置口径为：难度不高于 3 对应 1 级，不高于 5 对应 2 级，不高于 10 对应 3 级，不高于 20 对应 4 级，高于 20 对应 5 级。`toolGrade` 应在配置装载或校验阶段按该口径确定并固化，领奖时只读配置值，避免在多个领取入口重复计算。

因此活动等级与工具品级不存在必然相等关系：同属武士等级的赵三拳、鳌拜、陈近南可以分别掉落绿、蓝、黄工具；高级活动也只生成自身等级的模板，工具再按抽中的具体 BOSS 难度决定。6 级玩家暂归 5 级只影响参与分组，不代表工具强制为 5 级。

### 3.4 伤害规则

- BOSS 死亡时复制并冻结 `damages`，后续展示和奖励都读取快照；
- 随从伤害继续归属主人；
- 奖励计算使用 `clamp(damage / maxHp, 0, 1)`，不能把超过 100% 的占比改成 80%；
- 不在本次直接修改全局 `CHARACTER.damage()` 的记录语义，先在世界 BOSS 结算层规整溢出伤害，避免影响襄阳和其他战斗；
- 若以后要让全局伤害记录只累计实际扣血量，应单独立项并覆盖 `damage`、`damage2` 和所有消费方测试。

当前已确认的伤害规则：

- 有有效伤害但不足 1%：安慰奖，不消耗每日次数；
- 达到 1%：基础完整奖励；
- 奖励概率最多按 100% 伤害计算。

快速完成使用独立的 10% 门槛：达到该只 BOSS 最大气血 10% 的玩家，才会在活动面板中获得快速完成资格。

### 3.5 活动事件

每个活动槽必须包含等级和当前 BOSS 批次，但活动槽本身 24 小时常驻。建议 ID 保持等级槽稳定，例如：

```text
world_boss_<grade>
```

要求：

- 有当前 BOSS 时，活动按钮为“前往挑战”，点击后始终执行传送资格检查；
- BOSS 死亡后，活动按钮切换为“快速完成”，点击先弹出确认提示；
- 快速完成只对输出达到 10% 的玩家开放，未达标玩家仍可通过尸体领取符合其伤害档位的奖励；
- 下一只同等级 BOSS 出现时，活动槽重新切换为“前往挑战”，上一个 BOSS 的快速完成入口关闭；
- 活动列表 24 小时常驻，不因死亡立即移除，也不因普通领取窗口到期隐藏；
- 活动不受 BOSS 当前存活时间限制，玩家可随时打开活动面板；有 BOSS 时执行传送，无 BOSS 时执行上一个 BOSS 的快速完成；
- 活动命令执行时再次检查当前活动槽状态和等级资格，不能只依赖活动列表展示时的过滤；
- `run()`、`stop()`、热更新、创建失败和 BOSS 替换都必须调用统一 `cleanupRuntime()`；
- 不在模块顶层缓存 `TASK.GET('boss')`，活动回调必须引用当前任务实例或运行实例。

### 3.6 出生房间

世界 BOSS 保持现有公共房间范围，不改变不同品级的出生范围；修复重点是同一轮不能刷在同一房间，并排除明确不可战斗的位置。实现上可以继续使用统一候选池：

```ts
const WORLD_BOSS_ROOMS: Record<BossGrade, string[]> = {
    1: [...统一公共范围],
    2: [...统一公共范围],
    3: [...统一公共范围],
    4: [...统一公共范围],
    5: [...统一公共范围],
    6: [...统一公共范围，武神待办],
};
```

候选房间必须满足：

- 房间存在且不是副本、投影房或私人房；
- `no_fight !== true`；
- 容量足以容纳 BOSS 和预期玩家；
- 玩家能正常进入和离开；
- 不承载登录、交易、领奖、剧情锁定等关键功能；
- 地图区域与当前已有的开放范围相符；不新增或改变 `fb_index` / `min_fbindex` 门槛。

选房时为本轮维护 `usedRooms` 集合：

1. 从同一公共候选范围中随机抽取；
2. 已被本轮其他 BOSS 占用的房间跳过；
3. 只在候选全部耗尽时允许记录“无可用独立位置”，本轮对应等级不生成；
4. 不把“随机范围相同”误实现为“多个 BOSS 允许重叠出生”。

上线前逐个走通候选房间。候选为空或全部不可用时，本轮对应等级不生成 BOSS，并记录错误，不允许使用非空断言继续执行。

### 3.7 刷新时间

刷新时间必须配置化，并保持已确认的产品规则：

- 其他时段沿用现有每小时随机刷新；
- 21 点为 BOSS 狂欢夜，沿用现有约每 5 分钟刷新一次的规则；
- 活动槽 24 小时常驻；BOSS 死亡后直到下一只同等级 BOSS 出现前，活动用于上一个 BOSS 的快速完成；
- 没有合格在线玩家时跳过该等级，但不清除其他等级的常驻活动；
- 服务重启后的具体恢复实现可以另行处理，但不能留下失效活动。

修复应保持上述刷新频率和 21 点狂欢夜，不在本次调整产出量。先把时间计算抽成无副作用函数并增加测试；移除无效的 `week`、`quickly`、`boss_count` 等字段，或给它们补上明确用途。

## 4. 数据结构与接口方案

建议在 `boss_task.ts` 内先建立世界 BOSS 专用运行结构，不急于扩展通用 `TASK`：

```ts
interface BossRuntime {
    batchId: string;
    grade: BossGrade;
    state: 'active' | 'defeated' | 'quick-claimable' | 'cleaned';
    boss: NPC;
    room: ROOM;
    eventId: string;
    spawnedAt: number;
    replaceAt?: number;
    damageSnapshot?: Readonly<Record<string, number>>;
    rewards: Map<string, BossPlayerReward>;
}
```

`BossTask` 维护：

```ts
runtimes: Map<BossGrade, BossRuntime>;
nextTime: Date | null;
```

建议拆出的内部方法：

```ts
scheduleNext(now: Date): void;
collectEligibleUsers(): Map<BossGrade, USER[]>;
spawnBoss(grade: BossGrade, users: USER[]): BossRuntime | undefined;
selectBossRoom(grade: BossGrade): ROOM | undefined;
createChallengeEvent(runtime: BossRuntime): EventItem;
handleBossDefeated(runtime: BossRuntime, killer: USER | undefined, corpse: CORPSE): void;
claimBossReward(me: USER, runtime: BossRuntime, source: ClaimSource): ClaimResult;

```

不再在 `TASK` 基类声明世界 BOSS 专用的可选 `boss_auto_drops`。如果没有其他任务消费者，应删除该接口，防止“类型允许缺失、运行时静默跳过”。

## 5. 分阶段实施

### 阶段一：恢复结算闭环

目标：不改变 BOSS 数值和刷新频率，先保证玩家可以可靠领取且不会重复领取。

改动：

1. 删除模块顶层 `const BOSSTASK = TASK.GET('boss')`；
2. 在 `BossTask` 实例内实现统一领取入口；
3. 让尸体、自动拾取和活动领取共享奖励状态；
4. 将 `bcc` 增加移动到奖励成功交付之后；
5. 修复超过 100% 伤害被降为 80% 的逻辑；
6. 给活动槽设置真实的下一只同等级 BOSS 替换时间；
7. 增加快速完成的二次确认提示；
8. 领取回调返回明确结果，让活动面板可以刷新或提示；
9. 快速完成每次只完成一只 BOSS，连续点击、逐次确认，直到每日上限；
10. 将 BOSS 模板 `drop_list`、世界 BOSS 基础奖励和按模板难度生成的工具合并进同一份个人奖励快照；
11. 为工具池配置独立概率和数量，并解决藏宝箱资源缺口。

验收标准：

- 三个入口分别领取成功；
- 任意顺序混用三个入口仍只发一次；
- 背包满后可重试且不扣次数；
- 无伤害玩家不能领取；
- 每日第 6 次领取被拒绝；
- BOSS 死亡后活动仍显示为快速完成，直到下一只同等级 BOSS 出现；
- 快速完成未达到 10% 时被拒绝，达到 10% 时弹出确认；
- 背包满时快速完成被阻止且不扣次数；
- 确认一次只发放一次奖励，重复点击不会重复发奖。
- 尸体、自动拾取和快速完成拿到相同的模板掉落、基础奖励和工具快照；
- 工具品级严格等于当前模板的 `toolGrade`，并与其难度配置一致，不从玩家或活动等级推断。

### 阶段二：修复生命周期和房间

目标：消除旧活动闭包、重复出生和不可战斗出生点，同时保持活动槽常驻规则。

改动：

1. 引入 `BossRuntime` 和统一清理函数；
2. 为每轮生成唯一批次 ID；
3. 在刷新、停止、热更新、BOSS 替换和异常路径清理 BOSS 与事件；
4. 将 `ROOM.RANDOM()` 替换为同一公共范围内的候选池和 `usedRooms` 去重；
5. 单个等级创建失败时记录并继续其他等级，不直接中止整个刷新循环；
6. 清理死亡尸体和未领取奖励引用，避免长期占用内存。

验收标准：

- 连续刷新三轮后每个等级只有一个活动槽，且活动状态对应当前 BOSS 或上一个可快速完成的 BOSS；
- 某等级本轮没有在线玩家时不破坏其他等级活动槽，也不创建错误入口；
- 任务热更新不会留下旧 BOSS、旧事件或重复定时器；
- 同一轮多个 BOSS 不会出生在同一个房间；
- 一个等级创建失败不影响其他等级生成。

### 阶段三：统一当前等级兼容并保留武神 FIXME

目标：让当前 6 级归入 5 级的行为在活动、传送、攻击和领奖链路中一致；武神 BOSS 仅保留明确的 `FIXME` 待办，不在本阶段实现。

改动：

1. 引入统一的等级分桶和资格判断；
2. 活动、传送、`on_kill` 和领奖全部复用同一判断；
3. 在等级分组代码旁增加 `FIXME`，注明 6 级武神待办和当前暂归 5 级；
4. 将 `paths`、`player_levels`、`levels`、`boss_min_fb`、技能等级和奖励配置合并为显式 BOSS 模板配置；
5. 删除不可达的数组项、`create_boss2` 空声明和无消费者字段，或将武神字段明确标注为待办配置；
6. 保持现有 `fb_index` / `min_fbindex` 开放门槛；发现门槛 bug 时单独修复并增加测试，不在本计划中改变门槛设计。

推荐配置形态：

```ts
interface BossTemplateConfig {
    id: string;
    level: BossGrade;
    npcPath: string;
    difficulty: number;
    toolGrade: 1 | 2 | 3 | 4 | 5;
    minFbIndex?: number;
    skillLevel: number;
    reward: BossRewardConfig;
}

const templatesByLevel: ReadonlyMap<BossGrade, readonly BossTemplateConfig[]>;
```

验收标准：

- 所有在线等级都只进入一个明确分组；
- 每个活动等级只会抽到 `template.level` 完全相等的模板，高级场次不会刷新低级 BOSS；
- 模板池为空时安全跳过并记录配置错误，不向低等级模板池回退；
- 每个模板的 `difficulty`、`toolGrade` 和资源支持范围在启动时通过校验；
- 收到传闻的玩家一定能看到对应活动；
- 能进入活动的玩家一定符合攻击和领奖规则；
- 6 级玩家当前仍按 5 级参加，且活动、传送、攻击和领奖规则一致；
- 代码中保留明确的武神 BOSS `FIXME`，没有伪造武神活动；
- 所有保留配置都至少有一条可达路径和测试。

### 阶段四：刷新配置、可观测性和恢复策略

目标：让刷新规则可解释、可排障。

改动：

1. 将时间计算抽成纯函数和配置；
2. 日志记录批次、品级、房间、在线候选数、出生、死亡、领取和清理原因；
3. 增加异常指标：创建失败、无可用房间、奖励创建失败、领取重复、活动残留；
4. 明确服务重启策略；第一版可以不恢复旧 BOSS，但必须清空无效活动并重新计算下一场；
5. 如需固定场次补发，再将必要的批次元数据写入 `WORLD.DATA`，不要持久化 NPC 或物品对象。
