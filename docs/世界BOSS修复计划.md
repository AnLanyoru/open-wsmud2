# 世界 BOSS 修复计划

## 1. 目标与范围

本计划用于修复当前世界 BOSS 的活动、战斗、奖励和生命周期断链，并把等级、刷新和房间选择规则收敛为可验证的单一流程。

本次范围包括：

- 世界 BOSS 系统任务的刷新、停止和热更新生命周期；
- 在线玩家分组、活动可见性、传送和攻击资格；
- BOSS 死亡、伤害资格、尸体领取、自动拾取和活动面板快捷领取；
- 每日领取次数、领取幂等、活动过期和旧事件清理；
- 随机房间筛选、刷新时间配置、运行日志和专项测试。

本次不顺带调整普通 NPC、襄阳守城和门派战的奖励数值。若需要修改核心伤害记录，应先确认不会改变这些系统的既有结算结果。

## 2. 当前代码基线

| 环节 | 当前实现 | 当前问题 |
| --- | --- | --- |
| 定时刷新 | `server/res/task/boss_task.ts` 自行计算下一次时间 | 21 点密集刷新，其他时段每小时随机刷新；规则未配置化，存在无效字段 |
| 玩家分组 | 按玩家 `level` 分组，超过 5 级压到第 5 组 | 6 级玩家收到传闻，但活动、攻击和领取仍按严格等级判断 |
| BOSS 创建 | 从 4 个普通 NPC 模板克隆并重设属性 | 武帝、武神配置不可达，`create_boss2` 未实现，部分配置没有消费者 |
| 出生房间 | `ROOM.RANDOM()` | 只按容量粗筛，可能进入禁战或不适合群战的房间 |
| 活动入口 | 使用固定 ID `boss1` 至 `boss5` | 旧 BOSS 销毁时未移除活动，可能残留旧房间闭包 |
| 伤害记录 | 使用 `CHARACTER.damages` | 击杀溢出伤害可能使个人占比超过 100% |
| 尸体奖励 | 查看尸体时按玩家生成个人物品 | 查看即扣次数；领取失败也可能已扣次数；低伤害奖励不计次数 |
| 快捷领取 | 死亡后将活动按钮改为“领取” | `boss_auto_drops` 没有实现，按钮实际不发奖 |
| 任务引用 | 模块顶层执行 `TASK.GET('boss')` | 模块预加载早于任务实例化，引用会固定为 `undefined` |
| 自动拾取 | `WORLD.auto_get` 遍历死亡房间玩家 | 与手动尸体领取走同一生成入口，但没有统一的领取状态事务 |

当前关键调用链：

```text
BossTask.run()
    → check_users()
    → create_boss()
    → ROOM.RANDOM()
    → EVENTS.add(挑战活动)

NPC.die()
    → BossTask.on_died()（this 为 BOSS NPC）
    → 尸体注入 query_items / clear_items
    → EVENTS.add(领取活动)
    → WORLD.auto_get()
```

## 3. 修复后的目标行为

### 3.1 单次 BOSS 生命周期

每只 BOSS 必须具有唯一的运行批次和明确状态：

```text
scheduled → active → defeated → claimable → expired/cleaned
                  ↘ replaced/aborted → cleaned
```

- `active`：BOSS 存活，活动按钮为“前往挑战”；
- `defeated`：死亡回调冻结伤害快照，不再接受新的伤害变更；
- `claimable`：活动按钮为“领取”，尸体、自动拾取和活动领取共享同一领奖状态；
- `expired`：到达领取截止时间后删除活动、清空未领取的临时物品并释放 BOSS 引用；
- `replaced/aborted`：刷新替换、任务停止、热更新或创建失败时执行幂等清理。

任意状态下重复执行清理不得重复销毁对象、重复通知或抛出异常。

### 3.2 等级与参与资格

等级分桶、活动可见性、传送资格、攻击资格和领奖资格必须调用同一个函数，禁止分别使用 `===`、截断下标和 `on_kill` 独立推断。

建议定义：

```ts
type BossGrade = 1 | 2 | 3 | 4 | 5 | 6;

function getBossGrade(userLevel: number): BossGrade | undefined;
function canChallengeBoss(me: USER, boss: NPC): boolean;
```

实施前需要确认 6 级规则，推荐方案为：

1. 1 至 5 级玩家进入同级 BOSS；
2. 6 级及以上统一进入武神组；
3. 武神模板尚未配置完成时，不生成武神活动，也不向高等级玩家发送错误传闻；
4. 不再把 6 级玩家静默压到 5 级组。

如果产品决定暂不开放武神，第一阶段应明确排除 6 级玩家并给出可理解提示，不能保留当前半参与状态。

### 3.3 奖励与每日次数

尸体、自动拾取和活动面板必须调用同一个领取服务：

```ts
claimBossReward(me, runtime, source)
    → 校验批次和领取期限
    → 校验玩家等级与伤害资格
    → 校验当日次数
    → 获取或生成该玩家的奖励快照
    → 尝试放入背包
    → 成功后提交“已领取”和每日次数
    → 返回结构化结果
```

目标约束：

- 同一玩家、同一 BOSS 批次最多成功领取一次；
- 查看尸体只展示奖励，不增加 `bcc`；
- 背包满、物品创建失败或发放失败时不增加 `bcc`，奖励保持可重试；
- 尸体领取成功后再点活动“领取”，应提示已经领取，不能重复发奖；
- 自动拾取和手动领取同时触发时，必须由同一领取状态保证幂等；
- 推荐所有实际发放的奖励，包括低于 1% 的安慰奖，都计入每日 5 次额度；
- 如果产品要求安慰奖不计次数，需要另设每日安慰奖上限，避免无限低伤害领取；
- `bcc` 继续在每日 05:00 重置，与信息面板展示保持一致。

建议把动态的 `Record<string, OBJ[]>` 改为显式状态：

```ts
interface BossPlayerReward {
    state: 'eligible' | 'generated' | 'claimed';
    damage: number;
    damagePercent: number;
    items?: OBJ[];
    claimedAt?: number;
    source?: 'corpse' | 'auto' | 'event';
}
```

如果物品对象不适合跨较长时间保存在内存中，可以保存确定后的奖励描述，在真正交付时创建物品；但必须保证重试不会重新抽奖。

### 3.4 伤害规则

- BOSS 死亡时复制并冻结 `damages`，后续展示和奖励都读取快照；
- 随从伤害继续归属主人；
- 奖励计算使用 `clamp(damage / maxHp, 0, 1)`，不能把超过 100% 的占比改成 80%；
- 不在本次直接修改全局 `CHARACTER.damage()` 的记录语义，先在世界 BOSS 结算层规整溢出伤害，避免影响襄阳和其他战斗；
- 若以后要让全局伤害记录只累计实际扣血量，应单独立项并覆盖 `damage`、`damage2` 和所有消费方测试。

伤害门槛需要产品最终确认。为兼容当前数值，第一阶段建议保持：

- 有有效伤害但不足 1%：安慰奖；
- 达到 1%：基础完整奖励；
- 奖励概率最多按 100% 伤害计算。

### 3.5 活动事件

每个事件必须包含 BOSS 批次，不再只用等级作为唯一身份。建议 ID：

```text
world_boss_<batchId>_<grade>
```

要求：

- 挑战活动闭包只引用当前 `BossRuntime`，不引用可被下一轮替换的裸房间或旧 BOSS；
- BOSS 死亡时原地更新为领取活动，或先移除再添加同批次领取活动；
- 领取截止时间从运行实例传入，不在模块顶层缓存 `TASK.GET('boss')`；
- `run()`、`stop()`、热更新、创建失败和领取到期都必须调用统一 `cleanupRuntime()`；
- 活动命令执行时再次检查 `event.check(me)` 或等价资格，不能只依赖活动列表展示时的过滤；
- 玩家点击旧活动时返回“本轮 BOSS 已结束”，不能传送到旧房间或静默无响应。

### 3.6 出生房间

世界 BOSS 不应直接从全部公共房间均匀随机。推荐建立显式房间池：

```ts
const WORLD_BOSS_ROOMS: Record<BossGrade, string[]> = {
    1: [...],
    2: [...],
    3: [...],
    4: [...],
    5: [...],
    6: [...],
};
```

候选房间必须满足：

- 房间存在且不是副本、投影房或私人房；
- `no_fight !== true`；
- 容量足以容纳 BOSS 和预期玩家；
- 玩家能正常进入和离开；
- 不承载登录、交易、领奖、剧情锁定等关键功能；
- 地图区域与对应境界的开放进度相符。

上线前逐个走通白名单房间。白名单为空或全部不可用时，本轮对应等级不生成 BOSS，并记录错误，不允许使用非空断言继续执行。

### 3.7 刷新时间

刷新时间必须配置化，并明确以下产品选择：

- 是否全天每小时刷新；
- 21 点是否为特殊高频时段；
- 同一只 BOSS 的存活时长和死亡后的领取时长；
- 没有合格在线玩家时是否跳过该等级；
- 服务重启后是否补发错过的固定场次。

在产品确认前，修复应保持现有刷新频率，先把计算抽成无副作用函数并增加测试，避免在修 Bug 时同时改变产出量。移除无效的 `week`、`quickly`、`boss_count` 等字段，或给它们补上明确用途。

## 4. 数据结构与接口方案

建议在 `boss_task.ts` 内先建立世界 BOSS 专用运行结构，不急于扩展通用 `TASK`：

```ts
interface BossRuntime {
    batchId: string;
    grade: BossGrade;
    state: 'active' | 'defeated' | 'claimable' | 'cleaned';
    boss: NPC;
    room: ROOM;
    eventId: string;
    spawnedAt: number;
    claimUntil: number;
    damageSnapshot?: Readonly<Record<string, number>>;
    rewards: Map<string, BossPlayerReward>;
}
```

`BossTask` 维护：

```ts
runtimes: Map<BossGrade, BossRuntime>;
nextTime: Date | null;
```

建议拆出的内部方法：

```ts
scheduleNext(now: Date): void;
collectEligibleUsers(): Map<BossGrade, USER[]>;
spawnBoss(grade: BossGrade, users: USER[]): BossRuntime | undefined;
selectBossRoom(grade: BossGrade): ROOM | undefined;
createChallengeEvent(runtime: BossRuntime): EventItem;
handleBossDefeated(runtime: BossRuntime, killer: USER | undefined, corpse: CORPSE): void;
claimBossReward(me: USER, runtime: BossRuntime, source: ClaimSource): ClaimResult;
cleanupRuntime(runtime: BossRuntime, reason: CleanupReason): void;
```

不再在 `TASK` 基类声明世界 BOSS 专用的可选 `boss_auto_drops`。如果没有其他任务消费者，应删除该接口，防止“类型允许缺失、运行时静默跳过”。

## 5. 分阶段实施

### 阶段一：恢复结算闭环

目标：不改变 BOSS 数值和刷新频率，先保证玩家可以可靠领取且不会重复领取。

改动：

1. 删除模块顶层 `const BOSSTASK = TASK.GET('boss')`；
2. 在 `BossTask` 实例内实现统一领取入口；
3. 让尸体、自动拾取和活动领取共享奖励状态；
4. 将 `bcc` 增加移动到奖励成功交付之后；
5. 修复超过 100% 伤害被降为 80% 的逻辑；
6. 给领取活动设置真实截止时间；
7. 领取回调返回明确结果，让活动面板可以刷新或提示。

验收标准：

- 三个入口分别领取成功；
- 任意顺序混用三个入口仍只发一次；
- 背包满后可重试且不扣次数；
- 无伤害玩家不能领取；
- 每日第 6 次领取被拒绝；
- 领取活动到期后不再显示。

### 阶段二：修复生命周期和房间

目标：消除旧活动、旧房间闭包和不可战斗出生点。

改动：

1. 引入 `BossRuntime` 和统一清理函数；
2. 为每轮生成唯一批次 ID；
3. 在刷新、停止、热更新、死亡到期和异常路径清理 BOSS 与事件；
4. 将 `ROOM.RANDOM()` 替换为经过确认的房间白名单；
5. 单个等级创建失败时记录并继续其他等级，不直接中止整个刷新循环；
6. 清理死亡尸体和未领取奖励引用，避免长期占用内存。

验收标准：

- 连续刷新三轮后活动列表只包含当前有效场次；
- 某等级本轮没有在线玩家时不会残留上一轮入口；
- 任务热更新不会留下旧 BOSS、旧事件或重复定时器；
- 所有白名单房间均可进入、战斗和离开；
- 一个等级创建失败不影响其他等级生成。

### 阶段三：统一等级和补齐武神

目标：彻底解决 6 级玩家半参与，并清理不可达配置。

改动：

1. 引入统一的等级分桶和资格判断；
2. 活动、传送、`on_kill` 和领奖全部复用同一判断；
3. 根据产品决定实现武神模板和奖励，或明确关闭高等级入口；
4. 将 `paths`、`levels`、`boss_min_fb`、技能等级和奖励配置合并为按品级声明的配置对象；
5. 删除不可达的数组项、`create_boss2` 空声明和无消费者字段；
6. 明确 `fb_index`、`min_fbindex` 的真实含义；需要副本进度门槛时真正执行校验，否则删除。

推荐配置形态：

```ts
interface BossGradeConfig {
    grade: BossGrade;
    npcPath: string;
    difficulty: number;
    minFbIndex?: number;
    skillLevel: number;
    rooms: string[];
    reward: BossRewardConfig;
}
```

验收标准：

- 所有在线等级都只进入一个明确分组；
- 收到传闻的玩家一定能看到对应活动；
- 能进入活动的玩家一定符合攻击和领奖规则；
- 6 级规则与产品定义一致；
- 所有保留配置都至少有一条可达路径和测试。

### 阶段四：刷新配置、可观测性和恢复策略

目标：让刷新规则可解释、可排障。

改动：

1. 将时间计算抽成纯函数和配置；
2. 日志记录批次、品级、房间、在线候选数、出生、死亡、领取和清理原因；
3. 增加异常指标：创建失败、无可用房间、奖励创建失败、领取重复、活动残留；
4. 明确服务重启策略；第一版可以不恢复旧 BOSS，但必须清空无效活动并重新计算下一场；
5. 如需固定场次补发，再将必要的批次元数据写入 `WORLD.DATA`，不要持久化 NPC 或物品对象。

## 6. 涉及文件

预计主要修改：

- `server/res/task/boss_task.ts`：生命周期、等级、活动、伤害快照、奖励和调度；
- `server/core/task/task.ts`：删除无实现的 `boss_auto_drops` 可选接口；
- `server/core/task/events.ts`：如现有接口不足，补充按 ID 更新/幂等移除或命令时资格复检；
- `server/core/item/corpse.ts`：仅在需要通用“个人奖励状态”接口时修改，优先避免把世界 BOSS 业务下沉；
- `server/res/cmd/extend/auto.ts`：自动拾取改为调用统一领取入口，或继续通过尸体入口但消费同一状态；
- `server/res/cmd/dialog/events.ts`：如需要，补充事件回调结果后的列表刷新；
- 世界 BOSS 专项测试文件：覆盖调度、生命周期、等级和领取幂等。

原则：

- 不把 BOSS 奖励规则硬编码进 `CORPSE`、`EVENTS` 或通用 `get` 命令；
- 通用层只提供生命周期和事务所需的最小能力；
- 不复制一套“快捷领取奖励”和一套“尸体奖励”。

## 7. 测试计划

### 7.1 调度测试

- 19:xx、20:xx、21:00、21:59、22:xx 的下一次时间均符合配置；
- 下一次时间永远晚于当前时间；
- `stop()` 后不存在活跃定时器；
- 热更新后只保留一个定时器。

### 7.2 等级测试

- 1 至 5 级正确分组；
- 6 级及以上按最终产品规则处理；
- 无等级、离线、已满 5 次玩家不会触发错误场次；
- 活动检查、传送、攻击和领奖结果完全一致。

### 7.3 生命周期测试

- 正常出生、死亡、领取到期和下一轮替换；
- BOSS 未死亡就被下一轮替换；
- 创建第 N 个等级失败，其他等级继续；
- `stop()`、热更新重复调用清理不报错；
- 旧事件不能传送，旧批次不能领奖。

### 7.4 奖励测试

- 0 伤害、低于 1%、1%、50%、100% 和溢出伤害；
- 玩家伤害、随从归属伤害和多人伤害；
- 手动尸体、自动拾取、活动领取及其并发组合；
- 查看但不拾取、背包满、物品创建失败、部分交付失败；
- 同一玩家重复领取、重新登录后重试；
- 每日第 5 次成功、第 6 次拒绝、05:00 后恢复；
- 低伤害安慰奖按最终规则正确计数。

### 7.5 房间测试

- 白名单中不存在 `no_fight`、副本、私人或不可进入房间；
- 房间容量不足时换选其他候选；
- 所有候选失效时安全跳过并产生日志；
- 活动传送后玩家可以正常发起 `kill`。

## 8. 验证与上线顺序

每个阶段完成后，按仓库规则执行：

1. 修改期间运行服务端 TypeScript 校验：

   ```bash
   npx tsc -p server/tsconfig.json --noEmit
   ```

2. 运行新增的世界 BOSS 专项测试；
3. 最终验证执行：

   ```bash
   node scripts/pack.mjs --binary
   ```

4. 在测试服缩短刷新和领取时间，完成至少三轮连续场次；
5. 检查活动列表、BOSS 数量、领取日志和玩家 `bcc`；
6. 恢复正式刷新配置后上线；
7. 上线首日重点观察重复发奖、活动残留、无可用房间和高等级玩家拒绝次数。

建议按“阶段一 → 阶段二 → 阶段三 → 阶段四”分别提交。阶段一、二属于阻断性修复，应优先上线；武神内容和刷新频率调整可以在产品规则确认后独立上线。

## 9. 实施前待确认事项

以下事项不应由开发静默猜测：

1. 6 级及以上玩家是否统一参加武神 BOSS；
2. 21 点是否确实需要每 5 分钟刷新；
3. 低于 1% 的安慰奖是否消耗每日次数；
4. 快捷领取是否直接入包，背包满时如何提示；
5. BOSS 死亡后的领取窗口时长；
6. 合格但离线的玩家是否允许重新登录后领取；
7. `fb_index` / `min_fbindex` 是否仍是正式的开放门槛；
8. 每个品级允许刷新的房间白名单。

在这些规则确认前，可以先完成阶段一、二中不改变数值和产出频率的基础设施与确定性 Bug 修复。

## 10. 完成定义

满足以下条件后，世界 BOSS 修复可以视为完成：

- 世界 BOSS 的刷新、战斗、死亡、领取和清理形成闭环；
- 三种领取入口共享同一份奖励和领取状态；
- 不存在查看扣次数、失败扣次数或重复发奖；
- 不存在高等级玩家收到消息却无法参与的状态；
- 不会生成到禁战房间；
- 旧 BOSS、旧活动、旧定时器和未领取物品引用均能按时清理；
- 所有等级、伤害边界、生命周期和领取幂等测试通过；
- TypeScript 校验和二进制最终打包通过；
- 测试服连续三轮场次没有活动残留、重复发奖或阻断性错误。
