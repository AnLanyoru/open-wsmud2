# 世界 BOSS 修复计划

## 1. 目标与范围

本计划用于修复当前世界 BOSS 的活动、战斗、奖励和生命周期断链，并把等级、刷新和房间选择规则收敛为可验证的单一流程。

本次范围包括：

- 世界 BOSS 系统任务的刷新、停止和热更新生命周期；
- 在线玩家分组、活动可见性、传送和攻击资格；
- BOSS 死亡、伤害资格、尸体领取、自动拾取和活动面板快捷领取；
- 每日领取次数、领取幂等、活动过期和旧事件清理；
- 随机房间筛选、刷新时间配置、运行日志和专项测试。

本次不顺带调整普通 NPC、襄阳守城和门派战的奖励数值。若需要修改核心伤害记录，应先确认不会改变这些系统的既有结算结果。

| 环节 | 当前实现 | 当前问题 |
| --- | --- | --- |

| 玩家分组 | 按玩家 `level` 分组，超过 5 级压到第 5 组 | 该行为暂时保留，代码中标记 `FIXME`，武神 BOSS 另立待办 |

| 出生房间 | `ROOM.RANDOM()` | 只按容量粗筛，可能进入禁战或不适合群战的房间 |
| 活动入口 | 使用固定 ID `boss1` 至 `boss5` | 活动槽 24 小时常驻；有当前 BOSS 时负责传送，无当前 BOSS 时负责上一个 BOSS 的快速完成 |
| 伤害记录 | 使用 `CHARACTER.damages` | 击杀溢出伤害可能使个人占比超过 100% |
| 尸体奖励 | 查看尸体时按玩家生成个人物品 | 查看即扣次数；领取失败也可能已扣次数；安慰奖也必须消耗次数 |

| 自动拾取 | `WORLD.auto_get` 遍历死亡房间玩家 | 与手动尸体领取走同一生成入口，但没有统一的领取状态事务 |

当前关键调用链：

```text
BossTask.run()
    → check_users()
    → create_boss()
    → ROOM.RANDOM()
    → EVENTS.add(挑战活动)

NPC.die()
    → BossTask.on_died()（this 为 BOSS NPC）
    → 尸体注入 query_items / clear_items
    → EVENTS.add(领取活动)
    → WORLD.auto_get()
```

## 3. 修复后的目标行为

### 3.1 BOSS 与活动槽生命周期

每只 BOSS 必须具有唯一的运行批次和明确状态；活动槽本身不随 BOSS 死亡删除，而是持续存在 24 小时：

```text
scheduled → active → defeated → quick-claimable → replaced/cleaned
                  ↘ aborted → cleaned
```

- `active`：BOSS 存活，活动按钮为“前往挑战”；
- `defeated`：死亡回调冻结伤害快照，不再接受新的伤害变更；
- `quick-claimable`：当前没有 BOSS，活动按钮为“快速完成”；只有该玩家对上一个 BOSS 的输出达到 10% 才可快速完成；
- `replaced`：下一只同等级 BOSS 出现，活动按钮切换回“前往挑战”，上一个 BOSS 的快速完成入口关闭；
- `aborted`：任务停止、热更新或创建失败时执行幂等清理；
- 活动槽 24 小时常驻，不因 BOSS 死亡立即删除，也不使用“领取截止时间”提前隐藏活动。

任意状态下重复执行清理不得重复销毁对象、重复通知或抛出异常。

### 3.2 等级与参与资格

等级分桶、活动可见性、传送资格、攻击资格和领奖资格必须调用同一个函数，禁止分别使用 `===`、截断下标和 `on_kill` 独立推断。

建议定义：

```ts
type BossGrade = 1 | 2 | 3 | 4 | 5 | 6;

function getBossGrade(userLevel: number): BossGrade | undefined;
function canChallengeBoss(me: USER, boss: NPC): boolean;
```

当前决策：

1. 1 至 5 级规则保持现状；
2. 6 级及以上暂时继续归入 5 级组；
3. 在等级分组代码旁增加 `// FIXME: 6级武神 BOSS 待办，暂沿用5级分组`；
4. 武神 BOSS 的模板、奖励、开放条件和活动入口不在本次修复中实现，单独作为后续待办；
5. 活动、传送、攻击和领奖必须对当前“归入 5 级”的规则保持一致，不能出现收到传闻却无法参与的半参与状态。

### 3.3 奖励与每日次数

尸体、自动拾取和活动面板必须调用同一个领取服务。活动面板的“快速完成”是一次性操作，每次点击最多完成一只 BOSS：

```ts
claimBossReward(me, runtime, source)
    → 校验批次和活动当前状态
    → 校验玩家等级与伤害资格
    → 校验当日次数
    → 快速完成额外校验该玩家输出达到该 BOSS 最大气血的 10%
    → 向玩家弹出确认提示，确认后继续本次操作
    → 获取或生成该玩家的奖励快照
    → 检查背包容量，背包满时阻止领取
    → 尝试放入背包
    → 成功后提交“已领取”和每日次数
    → 返回结构化结果
```

目标约束：

- 同一玩家、同一 BOSS 批次最多成功领取一次；
- 查看尸体只展示奖励，不增加 `bcc`；
- 背包满时快速完成直接阻止领取，不弹出已完成或扣次数结果；
- 物品创建失败或发放失败时不增加 `bcc`，奖励保持可重试；
- 尸体领取成功后再点活动快速完成，应提示已经领取，不能重复发奖；
- 自动拾取和手动领取同时触发时，必须由同一领取状态保证幂等；
- 所有实际发放的奖励，包括低于 1% 的安慰奖，都计入每日 5 次额度；
- 快速完成每次只处理一只 BOSS；玩家可以重复点击并逐次确认，直到达到每日上限；
- `bcc` 继续在每日 05:00 重置，与信息面板展示保持一致。

建议把动态的 `Record<string, OBJ[]>` 改为显式状态：

```ts
interface BossPlayerReward {
    state: 'eligible' | 'generated' | 'claimed';
    damage: number;
    damagePercent: number;
    items?: OBJ[];
    claimedAt?: number;
    source?: 'corpse' | 'auto' | 'event';
}
```

如果物品对象不适合跨较长时间保存在内存中，可以保存确定后的奖励描述，在真正交付时创建物品；但必须保证重试不会重新抽奖。

### 3.4 伤害规则

- BOSS 死亡时复制并冻结 `damages`，后续展示和奖励都读取快照；
- 随从伤害继续归属主人；
- 奖励计算使用 `clamp(damage / maxHp, 0, 1)`，不能把超过 100% 的占比改成 80%；
- 不在本次直接修改全局 `CHARACTER.damage()` 的记录语义，先在世界 BOSS 结算层规整溢出伤害，避免影响襄阳和其他战斗；
- 若以后要让全局伤害记录只累计实际扣血量，应单独立项并覆盖 `damage`、`damage2` 和所有消费方测试。

当前已确认的伤害规则：

- 有有效伤害但不足 1%：安慰奖；
- 达到 1%：基础完整奖励；
- 奖励概率最多按 100% 伤害计算。

快速完成使用独立的 10% 门槛：达到该只 BOSS 最大气血 10% 的玩家，才会在活动面板中获得快速完成资格。

### 3.5 活动事件

每个活动槽必须包含等级和当前 BOSS 批次，但活动槽本身 24 小时常驻。建议 ID 保持等级槽稳定，例如：

```text
world_boss_<grade>
```

要求：

- 有当前 BOSS 时，活动按钮为“前往挑战”，点击后始终执行传送资格检查；
- BOSS 死亡后，活动按钮切换为“快速完成”，点击先弹出确认提示；
- 快速完成只对输出达到 10% 的玩家开放，未达标玩家仍可通过尸体领取符合其伤害档位的奖励；
- 下一只同等级 BOSS 出现时，活动槽重新切换为“前往挑战”，上一个 BOSS 的快速完成入口关闭；
- 活动列表 24 小时常驻，不因死亡立即移除，也不因普通领取窗口到期隐藏；
- 活动不受 BOSS 当前存活时间限制，玩家可随时打开活动面板；有 BOSS 时执行传送，无 BOSS 时执行上一个 BOSS 的快速完成；
- 活动命令执行时再次检查当前活动槽状态和等级资格，不能只依赖活动列表展示时的过滤；
- `run()`、`stop()`、热更新、创建失败和 BOSS 替换都必须调用统一 `cleanupRuntime()`；
- 不在模块顶层缓存 `TASK.GET('boss')`，活动回调必须引用当前任务实例或运行实例。

### 3.6 出生房间

世界 BOSS 保持现有公共房间范围，不改变不同品级的出生范围；修复重点是同一轮不能刷在同一房间，并排除明确不可战斗的位置。实现上可以继续使用统一候选池：

```ts
const WORLD_BOSS_ROOMS: Record<BossGrade, string[]> = {
    1: [...统一公共范围],
    2: [...统一公共范围],
    3: [...统一公共范围],
    4: [...统一公共范围],
    5: [...统一公共范围],
    6: [...统一公共范围，武神待办],
};
```

候选房间必须满足：

- 房间存在且不是副本、投影房或私人房；
- `no_fight !== true`；
- 容量足以容纳 BOSS 和预期玩家；
- 玩家能正常进入和离开；
- 不承载登录、交易、领奖、剧情锁定等关键功能；
- 地图区域与当前已有的开放范围相符；不新增或改变 `fb_index` / `min_fbindex` 门槛。

选房时为本轮维护 `usedRooms` 集合：

1. 从同一公共候选范围中随机抽取；
2. 已被本轮其他 BOSS 占用的房间跳过；
3. 只在候选全部耗尽时允许记录“无可用独立位置”，本轮对应等级不生成；
4. 不把“随机范围相同”误实现为“多个 BOSS 允许重叠出生”。

上线前逐个走通候选房间。候选为空或全部不可用时，本轮对应等级不生成 BOSS，并记录错误，不允许使用非空断言继续执行。

### 3.7 刷新时间

刷新时间必须配置化，并保持已确认的产品规则：

- 其他时段沿用现有每小时随机刷新；
- 21 点为 BOSS 狂欢夜，沿用现有约每 5 分钟刷新一次的规则；
- 活动槽 24 小时常驻；BOSS 死亡后直到下一只同等级 BOSS 出现前，活动用于上一个 BOSS 的快速完成；
- 没有合格在线玩家时跳过该等级，但不清除其他等级的常驻活动；
- 服务重启后的具体恢复实现可以另行处理，但不能留下失效活动。

修复应保持上述刷新频率和 21 点狂欢夜，不在本次调整产出量。先把时间计算抽成无副作用函数并增加测试；移除无效的 `week`、`quickly`、`boss_count` 等字段，或给它们补上明确用途。

## 4. 数据结构与接口方案

建议在 `boss_task.ts` 内先建立世界 BOSS 专用运行结构，不急于扩展通用 `TASK`：

```ts
interface BossRuntime {
    batchId: string;
    grade: BossGrade;
    state: 'active' | 'defeated' | 'quick-claimable' | 'cleaned';
    boss: NPC;
    room: ROOM;
    eventId: string;
    spawnedAt: number;
    replaceAt?: number;
    damageSnapshot?: Readonly<Record<string, number>>;
    rewards: Map<string, BossPlayerReward>;
}
```

`BossTask` 维护：

```ts
runtimes: Map<BossGrade, BossRuntime>;
nextTime: Date | null;
```

建议拆出的内部方法：

```ts
scheduleNext(now: Date): void;
collectEligibleUsers(): Map<BossGrade, USER[]>;
spawnBoss(grade: BossGrade, users: USER[]): BossRuntime | undefined;
selectBossRoom(grade: BossGrade): ROOM | undefined;
createChallengeEvent(runtime: BossRuntime): EventItem;
handleBossDefeated(runtime: BossRuntime, killer: USER | undefined, corpse: CORPSE): void;
claimBossReward(me: USER, runtime: BossRuntime, source: ClaimSource): ClaimResult;
cleanupRuntime(runtime: BossRuntime, reason: CleanupReason): void;
```

不再在 `TASK` 基类声明世界 BOSS 专用的可选 `boss_auto_drops`。如果没有其他任务消费者，应删除该接口，防止“类型允许缺失、运行时静默跳过”。

## 5. 分阶段实施

### 阶段一：恢复结算闭环

目标：不改变 BOSS 数值和刷新频率，先保证玩家可以可靠领取且不会重复领取。

改动：

1. 删除模块顶层 `const BOSSTASK = TASK.GET('boss')`；
2. 在 `BossTask` 实例内实现统一领取入口；
3. 让尸体、自动拾取和活动领取共享奖励状态；
4. 将 `bcc` 增加移动到奖励成功交付之后；
5. 修复超过 100% 伤害被降为 80% 的逻辑；
6. 给活动槽设置真实的下一只同等级 BOSS 替换时间；
7. 增加快速完成的二次确认提示；
8. 领取回调返回明确结果，让活动面板可以刷新或提示；
9. 快速完成每次只完成一只 BOSS，连续点击、逐次确认，直到每日上限。

验收标准：

- 三个入口分别领取成功；
- 任意顺序混用三个入口仍只发一次；
- 背包满后可重试且不扣次数；
- 无伤害玩家不能领取；
- 每日第 6 次领取被拒绝；
- BOSS 死亡后活动仍显示为快速完成，直到下一只同等级 BOSS 出现；
- 快速完成未达到 10% 时被拒绝，达到 10% 时弹出确认；
- 背包满时快速完成被阻止且不扣次数；
- 确认一次只发放一次奖励，重复点击不会重复发奖。

### 阶段二：修复生命周期和房间

目标：消除旧活动闭包、重复出生和不可战斗出生点，同时保持活动槽常驻规则。

改动：

1. 引入 `BossRuntime` 和统一清理函数；
2. 为每轮生成唯一批次 ID；
3. 在刷新、停止、热更新、BOSS 替换和异常路径清理 BOSS 与事件；
4. 将 `ROOM.RANDOM()` 替换为同一公共范围内的候选池和 `usedRooms` 去重；
5. 单个等级创建失败时记录并继续其他等级，不直接中止整个刷新循环；
6. 清理死亡尸体和未领取奖励引用，避免长期占用内存。

验收标准：

- 连续刷新三轮后每个等级只有一个活动槽，且活动状态对应当前 BOSS 或上一个可快速完成的 BOSS；
- 某等级本轮没有在线玩家时不破坏其他等级活动槽，也不创建错误入口；
- 任务热更新不会留下旧 BOSS、旧事件或重复定时器；
- 同一轮多个 BOSS 不会出生在同一个房间；
- 一个等级创建失败不影响其他等级生成。

### 阶段三：统一当前等级兼容并保留武神 FIXME

目标：让当前 6 级归入 5 级的行为在活动、传送、攻击和领奖链路中一致；武神 BOSS 仅保留明确的 `FIXME` 待办，不在本阶段实现。

改动：

1. 引入统一的等级分桶和资格判断；
2. 活动、传送、`on_kill` 和领奖全部复用同一判断；
3. 在等级分组代码旁增加 `FIXME`，注明 6 级武神待办和当前暂归 5 级；
4. 将 `paths`、`levels`、`boss_min_fb`、技能等级和奖励配置合并为按品级声明的配置对象；
5. 删除不可达的数组项、`create_boss2` 空声明和无消费者字段，或将武神字段明确标注为待办配置；
6. 保持现有 `fb_index` / `min_fbindex` 开放门槛；发现门槛 bug 时单独修复并增加测试，不在本计划中改变门槛设计。

推荐配置形态：

```ts
interface BossGradeConfig {
    grade: BossGrade;
    npcPath: string;
    difficulty: number;
    minFbIndex?: number;
    skillLevel: number;
    rooms: string[];
    reward: BossRewardConfig;
}
```

验收标准：

- 所有在线等级都只进入一个明确分组；
- 收到传闻的玩家一定能看到对应活动；
- 能进入活动的玩家一定符合攻击和领奖规则；
- 6 级玩家当前仍按 5 级参加，且活动、传送、攻击和领奖规则一致；
- 代码中保留明确的武神 BOSS `FIXME`，没有伪造武神活动；
- 所有保留配置都至少有一条可达路径和测试。

### 阶段四：刷新配置、可观测性和恢复策略

目标：让刷新规则可解释、可排障。

改动：

1. 将时间计算抽成纯函数和配置；
2. 日志记录批次、品级、房间、在线候选数、出生、死亡、领取和清理原因；
3. 增加异常指标：创建失败、无可用房间、奖励创建失败、领取重复、活动残留；
4. 明确服务重启策略；第一版可以不恢复旧 BOSS，但必须清空无效活动并重新计算下一场；
5. 如需固定场次补发，再将必要的批次元数据写入 `WORLD.DATA`，不要持久化 NPC 或物品对象。

- `server/core/task/events.ts`：如现有接口不足，补充按 ID 更新/幂等移除或命令时资格复检；
- `server/core/item/corpse.ts`：仅在需要通用“个人奖励状态”接口时修改，优先避免把世界 BOSS 业务下沉；
- `server/res/cmd/extend/auto.ts`：自动拾取改为调用统一领取入口，或继续通过尸体入口但消费同一状态；
- `server/res/cmd/dialog/events.ts`：补充快速完成确认提示和活动槽状态刷新；
- 世界 BOSS 专项测试文件：覆盖调度、生命周期、等级和领取幂等。

原则：

- 不把 BOSS 奖励规则硬编码进 `CORPSE`、`EVENTS` 或通用 `get` 命令；
- 通用层只提供生命周期和事务所需的最小能力；
- 不复制一套“快捷领取奖励”和一套“尸体奖励”。

## 7. 测试计划

### 7.1 调度测试

- 19:xx、20:xx、21:00、21:59、22:xx 的下一次时间均符合配置；
- 下一次时间永远晚于当前时间；
- `stop()` 后不存在活跃定时器；
- 热更新后只保留一个定时器。

### 7.2 等级测试

- 1 至 5 级正确分组；
- 6 级及以上按最终产品规则处理；
- 无等级、离线、已满 5 次玩家不会触发错误场次；
- 活动检查、传送、攻击和领奖结果完全一致。

### 7.3 生命周期测试

- 正常出生、死亡、领取到期和下一轮替换；
- BOSS 未死亡就被下一轮替换；
- 创建第 N 个等级失败，其他等级继续；
- `stop()`、热更新重复调用清理不报错；
- 旧事件不能传送，旧批次不能领奖。

### 7.4 奖励测试

- 0 伤害、低于 1%、1%、50%、100% 和溢出伤害；
- 玩家伤害、随从归属伤害和多人伤害；
- 手动尸体、自动拾取、活动领取及其并发组合；
- 查看但不拾取、背包满、物品创建失败、部分交付失败；
- 同一玩家重复领取、重新登录后重试；
- 每日第 5 次成功、第 6 次拒绝、05:00 后恢复；
- 低伤害安慰奖按最终规则正确计数。

### 7.5 房间测试

- 候选公共范围中不存在 `no_fight`、副本、私人或不可进入房间；
- 房间容量不足时换选其他候选；
- 所有候选失效时安全跳过并产生日志；
- 活动传送后玩家可以正常发起 `kill`。

## 9. 已确认决策与技术待办

以下业务决策已经确认，实施时不得重新解释：

1. 6 级及以上当前继续归入 5 级；武神 BOSS 标记 `FIXME`，另立待办；
2. 21 点为 BOSS 狂欢夜，保持约每 5 分钟刷新；
3. 安慰奖照样消耗每日次数；
4. 快速完成要求单只 BOSS 输出达到 10%，点击后弹出确认，每次确认完成一次，直到每日上限；
5. 背包满时阻止快速完成，不扣次数、不标记已完成；
6. 活动不因时间限制关闭，活动槽 24 小时常驻；
7. BOSS 死亡后一直可以领取，直到下一只同等级 BOSS 出现；
8. 有 BOSS 时活动按钮为传送，无 BOSS 时活动按钮为上一个 BOSS 的快速完成；
9. 现有开放门槛保持不变，发现门槛 bug 时只修复错误实现；
10. 所有品级保持同一公共出生范围，同一轮不同 BOSS 不得出生在同一房间。

仍需在实现阶段落实的技术细节：

- 客户端确认提示沿用现有命令/确认交互协议，确认后只提交一次快速完成；
- 活动槽切换必须是幂等的，不能因死亡回调或刷新回调重复发放；
- 下一只 BOSS 出现时清理上一个 BOSS 的快速完成状态，但不影响已成功发放的奖励记录；
- 开放门槛判断要补充边界测试，尤其是 `fb_index` 缺失、非法和跨等级场景。
