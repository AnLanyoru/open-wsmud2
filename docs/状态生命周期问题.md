# 状态生命周期问题

## 1. 问题概述

`busy`、`faint`、`rash`、`shadow`（以及同类的 `miss`、`ig_control`）目前采用“双挂载”模型：

1. buff 本身保存在角色的 `status[]` 中，按 `id` 管理生命周期、定时器、叠层和 UI 展示。
2. buff 的 `change_buff()` 同时把效果镜像到角色类字段，例如 `is_busy`、`is_faint`、`is_rash`、`is_shadow`。

角色类字段是单值，不能表达“哪些 buff 正在提供该效果”。因此不同 `id` 但相同 `is_*` 标记的状态会互相覆盖：

```text
添加 A（id=a, is_busy=true, 3 秒） -> is_busy=3000
添加 B（id=b, is_busy=true, 5 秒） -> is_busy=5000
A 到期并卸载                      -> is_busy=0
                                      但 B 仍在 status[] 中
```

最终表现为状态列表仍显示 B，但战斗和指令判断已经认为角色不 busy。相反，如果 B 先结束，也会错误地清除 A。

## 2. 当前代码流程与影响范围

主要流程位于 `server/core/char/character.ts`：

- `add_status()` 将状态按 `id` 放入 `status[]`，并注册 `remove_status(sid)` 定时器。
- `remove_status()` 找到指定 `id` 后调用 `change_buff(item, false, ...)`，随后从数组移除。
- `change_buff(item, true)` 直接写入角色类标记的持续时间。
- `change_buff(item, false)` 无条件将对应标记写成 `0`。

受影响的行为包括：

- `can_attack()`、自动攻击循环和技能释放限制；
- 招架、闪避、绝对命中等战斗判定；
- 普通指令的 `allow_busy` / `allow_faint` 检查；
- 批量清除、战斗结束清除、状态刷新和叠层状态；
- 仍存在的直接赋值路径（例如部分技能直接写 `me.is_rash = ...`），它们与 buff 托管没有来源关联。

特别需要注意：同一 `id` 的 `override: 1` 叠层在减少一层时也会先调用一次卸载逻辑，因此并非只有“不同 id”才会触发问题。

## 3. 方案评价标准

方案至少需要满足：

1. 每个状态来源独立结束，不得清除其他仍存活来源；
2. 同一 `id` 的叠层、刷新和替换语义保持一致；
3. 批量清除、战斗清除和异常结束不会留下错误镜像；
4. 角色字段的现有调用方尽量无需大规模改写；
5. 状态持续时间、减免、来源加成和定时器只有一个权威计算点；
6. 可测试，且能发现直接赋值绕过状态系统的路径。

## 4. 更推荐的长期方案：状态集合为唯一事实源

不要让单个 buff 在卸载时直接执行 `is_busy = 0`。`status[]` 应作为事实源，角色类字段只是由所有当前有效 buff 聚合出的兼容镜像。

### 4.1 聚合规则

为每个共享标记提供统一重算函数，例如 `sync_status_flags()`：

- 遍历当前仍在 `status[]` 中的 buff；
- 对声明了该标记的 buff 计算剩余时间；
- 取所有来源的最大剩余时间；
- 没有来源时才写 `0`。

如果保留现有数字字段，聚合结果仍应是“最长剩余时间”，而不是最后添加者的持续时间。建议给状态增加明确的 `expire_time`（或等价内部字段），避免通过 `start_time + duration` 猜测 `on_interval` 等特殊状态的结束时间。

### 4.2 生命周期调整

`change_buff()` 只负责该 buff 独占的副作用：属性、回调、消息和临时数据；共享 `is_*` 标记不在这里直接清零。状态数组完成添加、替换、叠层减少或批量删除后，统一调用一次 `sync_status_flags()`。

这样可以自然覆盖：

- 不同 id 的同类状态重叠；
- `override: 1` 剩余层数；
- `override: 2` 刷新替换；
- `clear_downside()`、`remove_statuses()`、`clear_combat_status()`；
- 同时存在 busy/faint/rash/shadow 的组合。

### 4.3 直接赋值迁移

有明确生命周期的 `me.is_rash = duration`、`target.is_busy = duration` 等代码应迁移为内部 buff。若不希望显示在客户端，可增加 `hidden/internal` 属性，而不是继续绕过状态系统。短期可保留兼容接口，但必须带来源 token，不能再裸写共享字段。

## 5. 对“托管退避/接管”方案的分析

提议：在一个 buff 接管角色类 `is` 状态前，调用判定函数，传入状态键和持续时间：

1. 如果不可接管，则删除自身的 `is` 标记；
2. 如果可接管，则删除所有 buff 的该 `is` 标记，由当前 buff 接管。

### 5.1 可取之处

- 改动集中在状态接管点，现有消费 `is_busy` 等字段的代码可以继续工作；
- 若产品语义明确要求“同一时刻只能有一个控制来源”，接管模型比简单清零更接近该语义；
- 可以把优先级、持续时间比较和刷新策略集中在一个判定函数中。

### 5.2 关键问题

该方案实际上改变了游戏语义：它不是修复“重叠状态”，而是把同类状态设计成“互斥、抢占”。如果 A 与 B 本应同时存在，接管时删除 A 的 `is` 标记会造成：

- A 仍留在 `status[]`，但其声明与实际效果不一致；
- A 到期时仍会触发回调、消息、属性卸载，生命周期和镜像脱钩；
- B 先结束时无法恢复 A，除非额外保存被接管栈并重新接管；
- `override: 1` 叠层、`override: 2` 替换、批量删除都需要维护复杂的接管关系；
- “删除所有 buff 的该 is 标记”会修改状态定义本身，导致状态对象被复用或再次叠加时出现脏数据；
- 直接赋值路径没有 buff 身份，仍然无法与接管判定统一；
- 定时器执行顺序可能产生短暂空窗：旧 buff 被摘标记后，新 buff 尚未完成接管，战斗线程可能观察到错误状态。

因此，如果“不可接管”时只是删除当前 buff 的 `is` 标记，状态列表会显示一个实际不生效的 buff；如果“可接管”时删除其他 buff 的标记，则必须实现可恢复的优先级栈，复杂度接近重新实现状态系统。

### 5.3 何时适合使用

接管模型只适合明确的互斥控制效果，例如“硬控槽位”或“同类效果只取最高级”，并且应定义：

- 优先级/比较规则（持续时间、来源等级或显式 priority）；
- 被抢占状态是否暂停、缩短、彻底移除；
- 当前接管者结束后是否恢复上一层；
- UI 是否展示所有候选状态，还是只展示生效状态；
- 外部直接赋值如何获得 token。

它不适合作为当前所有 `is_*` 标记的通用修复方案。

## 6. 折中方案：来源租约 + 聚合镜像

如果暂时不能把所有直接赋值迁移成 buff，可增加内部“状态租约”：

```text
attach_state(flag, sourceToken, duration)
detach_state(flag, sourceToken)
```

角色保存 `flag -> sourceToken -> expireTime`，对外仍提供 `is_*` 数字镜像，并按最长剩余时间聚合。普通 buff 和临时技能效果都通过租约接入，结束时只能释放自己的 token。

这是安全的过渡方案，但最终仍建议统一收敛到 `status[]`，避免同时维护 buff、租约和裸字段三套模型。

## 7. 建议落地顺序

1. 先补回归测试，复现不同 id 重叠和同 id 叠层提前清零；
2. 抽出 `sync_status_flags()`，先停止 `change_buff(false)` 的无条件清零；
3. 为状态记录明确 `expire_time`，统一处理刷新、叠层和 `on_interval`；
4. 将直接写 `is_*` 的技能迁移为内部 buff 或带 token 的租约；
5. 对确实需要互斥的效果，再在聚合层增加 `priority/stackingGroup`，不要用“删除其他 buff 的标记”实现隐式接管；
6. 增加状态生命周期、批量清除、战斗结束和并发定时器测试。

## 8. 结论

“托管退避/接管”可以作为特定互斥控制效果的策略，但不应作为所有 `is` 类状态的底层修复。更稳妥的基础设施是：**buff 保留自己的声明和生命周期，角色类状态由当前有效来源聚合计算；任何单个 buff 都无权直接清除共享状态。**

## 9. 兼顾性能与优雅性的最终方案

如果不考虑代码修改量，建议采用“状态实例 + 效果贡献索引 + 派生角色状态”的三层模型，而不是每次变更都扫描整个 `status[]`。

### 9.1 三层职责

```text
StatusInstance（状态实例）
  ├─ 生命周期、叠加、刷新、回调、UI 展示
  └─ instanceId 唯一，不再只依赖 sid 识别定时器

EffectContribution（效果贡献）
  ├─ instanceId / layerId
  ├─ effectKey：busy、faint、rash、shadow、miss、ig_control
  ├─ expireAt、priority、stackingGroup
  └─ active 标记

ResolvedState（角色派生状态）
  ├─ is_busy、is_faint 等现有兼容字段
  └─ 只读地由贡献索引解析得到
```

`status[]` 负责“有哪些状态以及如何展示”；控制效果查询走按 `effectKey` 建立的索引。角色的 `is_*` 字段不再由单个 buff 直接写入。

### 9.2 高性能索引

角色内部维护 `Map<effectKey, EffectBucket>`。每个 bucket 保存有效贡献，并维护按 `expireAt`（必要时再按 `priority`）排序的最大堆：

- 添加贡献：写入 token 并入堆，O(log n)；
- 移除贡献：只将 token 标记为 inactive，O(1)；
- 查询/重算：惰性弹出失效或过期 token，均摊 O(log n)；
- 读取 `is_busy` 等字段：读取缓存的 `ResolvedState`，O(1)。

当前控制来源通常很少，也可以使用“当前 winner + 备用堆”，只有 winner 失效时才选下一个来源。

### 9.3 解析策略

- `busy/faint/rash/shadow/miss/ig_control`：同类贡献默认取 `expireAt` 最大者，角色字段为其剩余时间；
- 不同 `effectKey` 互不影响；
- 需要互斥时，通过显式 `stackingGroup` 和 `priority` 选 winner；
- 被淘汰的贡献仍保持自己的生命周期，是否隐藏、暂停或移除由策略决定，不能通过篡改其他 buff 的 `is_*` 标记实现。

### 9.4 原子更新与定时器

每次状态变更在一个原子事务内完成：

```text
更新 StatusInstance
 -> 增删对应 EffectContribution
 -> 解析受影响的 effectKey
 -> 更新 ResolvedState
 -> 一次性发送状态/UI 增量
```

定时器回调必须携带 `instanceId/layerId`，不能只传 `sid`。回调先校验 token 是否仍 active，避免旧定时器在刷新或替换后误删新状态。多个字段同时变化时只重算受影响的 bucket，不做全角色、全状态扫描。

### 9.5 直接效果统一接入

原先直接写 `me.is_rash = duration` 的技能，也通过同一个 `EffectContribution` API 接入；不展示给客户端的效果使用 `internal` 标记。buff、技能临时控制、房间机制都拥有统一 source token，结束时只能释放自己的 token。

### 9.6 为什么优于“托管接管”

- 任一来源结束都不会误清其他来源；
- 不需要修改或删除其他 buff 的声明；
- 不需要维护隐式接管栈；
- 查询 O(1)，增删 O(log n) 或均摊 O(1)；
- 可以保留现有 `is_*` 数字字段，逐步迁移调用方；
- UI 状态和实际生效状态可以分别表达，不会出现列表与效果不一致。

这是在性能、可验证性和长期扩展性之间更平衡的底层方案。

## 10. 新方案：`is` 类改为结束时间戳，由框架统一判定

### 10.1 方案理解

新提议可以整理为以下模型：

1. `is_busy`、`is_faint`、`is_rash` 等不再保存“本次持续多少毫秒”，而保存该效果的绝对结束时间 `endAt`；
2. 每个状态实例也保存自己的效果结束时间；
3. 新状态生效时，角色上的同类结束时间取当前值与新状态 `endAt` 的较大者；
4. 调用方不直接解释时间戳，而通过框架接口查询“是否生效”或“还剩多久”，接口内部使用 `Date.now()` 自动处理过期；
5. 状态结束时，用自身 `endAt` 与角色当前托管的 `endAt` 比较，判断它是否可能是当前托管者，再决定是否清理或移交。

例如：

```text
A: busy 到 10:00:03       -> 角色 busyEndAt = 10:00:03
B: busy 到 10:00:05       -> 角色 busyEndAt = 10:00:05
A 在 10:00:03 自然结束    -> 不处理，当前值属于 B
B 在 10:00:05 自然结束    -> 查询接口发现 endAt <= now，返回未 busy
```

### 10.2 这个思路为什么成立

对于 `busy/faint/rash/shadow/miss/ig_control` 这类“同类来源只要有一个生效，角色就处于该状态”的布尔效果，只需要知道所有有效来源中最晚的结束时间：

```text
resolvedEndAt = max(source.effectEndAt)
```

新状态一定从当前时刻开始，因此新来源的有效区间与当前有效区间相交。只要添加时取最大 `endAt`，自然到期时就不需要恢复较早来源：当前最晚来源自然到期时，结束时间更早的来源也必然已经到期。

这比维护完整的“接管栈”简单，也比每次查询遍历 `status[]` 更便宜。新增是 O(1)，普通查询也是 O(1)。从当前业务语义看，这是一个可行且更贴近现有代码的方案。

### 10.3 查询接口必须区分“是否生效”和“剩余时间”

当前代码中的 `is_*` 有两种用途：

```ts
if (me.is_busy) { ... }                    // 布尔判断
call_out(me.auto_attack, me.is_busy)       // 当作剩余毫秒数
```

如果直接把公开的 `is_busy` 改成 Unix 毫秒时间戳，第二种调用会把约 `1.8e12` 当作延迟，造成攻击循环近似永久停住。因此框架接口至少要明确提供：

```text
has_effect("busy")          -> boolean
effect_remaining("busy")   -> max(0, endAt - Date.now())
effect_end_at("busy")       -> 内部绝对时间戳，仅生命周期系统使用
```

也可以为了降低迁移量，把现有 `is_busy` 做成只读 getter，仍返回“剩余毫秒数”，把真实时间戳保存在 `_busyEndAt`；这样现有布尔判断和定时调度大多可以保持不变。但外部 setter 必须取消，所有写入统一走框架接口，否则无法判断传入的是 duration 还是 endAt，也无法记录来源。

接口查询到 `endAt <= now` 时可返回 `0/false`，并惰性地把缓存归零。正确性应依赖时间比较，而不是依赖定时器恰好准时执行。

### 10.4 “结束时比较时间戳”只能作为快速路径

如果所有状态都只会自然到期，比较时间戳已经足够；但当前系统还存在驱散、战斗结束清除、批量清除、刷新替换和死亡清理。以下情况需要恢复较早但仍有效的来源：

```text
A: busyEndAt = 10:00:10
B: busyEndAt = 10:00:20（当前托管值）
10:00:05 时 B 被提前驱散
```

此时不能把角色值直接清零，因为 A 仍应生效到 `10:00:10`。正确规则应是：

```text
移除来源的 endAt < 当前 resolvedEndAt
    -> 它不是当前最晚来源，不重算

移除来源的 endAt >= 当前 resolvedEndAt
    -> 从剩余有效来源重算 max(endAt)
```

因此，“对比时间戳决定是否托管”适合用来判断是否需要重算，而不能在命中后直接清零。由于单个角色的状态数量通常很少，只在最晚来源被提前移除时扫描一次 `status[]`，实际成本很低：常规移除 O(1)，失去当前最晚来源时 O(n)。这可能比引入堆和 inactive token 更适合当前项目。

相等也必须按“需要重算”处理。两个来源可能恰好拥有相同 `endAt`，仅凭数值相等无法证明被移除状态是唯一托管者；重算会保留另一个同结束时间的来源。

### 10.5 状态自身应保存什么时间

建议不要复用含义模糊的 `duration`，而是在运行时状态上显式记录：

```text
startAt          状态本次开始/刷新时间
expireAt         状态实例的生命周期结束时间
effectEndAt      各 is 类效果的结束时间；当前同 duration 时可与 expireAt 相同
```

若一个状态中的所有 `is_*` 都与状态本身同时结束，一个 `expireAt` 即可，不必为每个标记重复保存。未来若同一状态的控制效果和 UI 生命周期不同，再拆成按 effect key 的结束时间。

时间戳必须在负面状态减免、施法者 busy 加成等持续时间计算全部完成后生成：

```text
先计算最终 duration
-> expireAt = Date.now() + duration
-> 注册以 expireAt 为依据的定时器
-> 提交到角色效果解析器
```

刷新时使用新的 `expireAt`；旧定时器回调必须校验该状态当前的 `expireAt`，避免旧回调删除已刷新的状态。

### 10.6 当前特殊生命周期的边界

- `override: 1`：当前一个状态对象代表多层，却只有一个定时器，逐层结束时会重新开始一段 `duration`。若保持该语义，每次减层后都要生成新的 `expireAt` 并重新提交；若希望每层独立到期，则必须为每层记录时间戳。
- `override: 2`：替换前不能先无条件释放共享效果；应先完成状态替换，再针对受影响的 effect key 解析一次，避免瞬时空窗。
- `on_interval`：当前 `duration` 表示间隔，而不一定表示整个状态的总寿命。不能简单令 `expireAt = now + duration` 并当作最终结束；应记录“下一次触发时间”和可计算的最终结束时间，或在每次间隔继续时更新效果时间戳。
- `duration === 0`：当前可能表示无定时结束。需要明确永久状态的表示方式，建议使用 `null` 或 `Infinity` 的内部语义，不要把 `0` 同时当作“未生效”和“永久”。若需要序列化，避免直接序列化 `Infinity`。
- 提前移除：必须先把待删除状态排除出事实源，再重算；否则扫描时会把它自己重新选为最大值。
- 批量删除：先完成数组变更，再对所有受影响的 effect key 各重算一次，不要每删一个状态就扫描一次。

### 10.7 直接赋值仍必须迁移

仓库里目前仍有技能和地图逻辑直接执行：

```text
target.is_busy = duration
me.is_rash = duration
稍后再赋值为 0
```

时间戳方案不能自动解决这些路径的来源冲突。例如某技能将全局 `busyEndAt` 延长后提前取消，框架不知道应该恢复哪个 buff 的值。它们需要统一迁移成以下两种形式之一：

1. 隐藏的内部状态，纳入 `status[]`；
2. 带唯一 source token 的临时效果注册接口。

只提供 `set_effect_end_at(key, endAt)` 而没有来源身份，只适合“只延长、绝不提前撤销”的效果；它无法正确支持按来源取消。

### 10.8 推荐的精简实现形态

在当前项目里，建议采用“状态时间戳 + 最大值缓存 + 必要时扫描重算”，无需一开始就实现最大堆：

```text
CharacterStatus.expireAt
        |
        v
status[] 作为来源事实集
        |
        +-- 添加/刷新：resolvedEndAt = max(resolvedEndAt, expireAt)
        |
        +-- 移除非最晚来源：无需重算
        |
        +-- 提前移除最晚来源：扫描剩余 status[] 取 max
        v
角色内部各 effectEndAt 缓存
        |
        +-- has_effect(key)
        +-- effect_remaining(key)
```

推荐的更新顺序是：

```text
完成 duration 修正并生成 expireAt
-> 原子地更新 status[]
-> 只解析受影响的 is 类 key
-> 再发送 UI 增量和执行后续调度
```

若后续证明单个角色存在大量同类来源，才把“扫描剩余来源”替换成堆；接口和状态数据模型不需要随之改变。

### 10.9 对新方案的结论

这个方案可行，而且在当前项目中很可能比第 9 节的完整贡献索引更合适。它抓住了共享 `is` 状态真正需要的量：**最晚结束时间，而不是最后写入者的持续时间**。

需要对原提议做两点修正：

1. 绝对时间戳应是内部事实，调用方通过“是否生效/剩余时间”接口读取，不能把时间戳直接当现有 `is_*` 数字使用；
2. 状态结束时比较时间戳只决定“是否需要重算”。自然到期可以惰性失效，但当前最晚来源被提前移除时，必须从剩余来源恢复新的最晚结束时间，不能直接清零。

满足这两点，再把裸赋值路径迁移到带来源的状态接口后，该方案能正确解决重叠状态提前清除问题，同时保持实现简单、查询快速，并为以后扩展显式优先级或独立效果贡献留下空间。

## 11. 将外置 `is_*` 改为 getter/setter 的合理性

### 11.1 结论先行

把 `is_busy`、`is_faint` 等公开字段改为 getter/setter，并在内部保存 `_busy_ts`、`_faint_ts`，是一个很好的**最小兼容层方案**：现有大量读取代码可以继续把 `is_*` 同时用于布尔判断和剩余时间调度。

但如果 setter 只接收一个数字并比较内部结束时间戳，它不是完整的生命周期方案，也不能称为全局最优方案。原因是 setter 知道“写了什么值”，却不知道“哪个来源在写”；尤其无法安全解释 `is_xxx = 0`。

准确评价是：

```text
getter：非常合适，优雅地兼容现有读取语义
正数 setter：适合作为只延长时间的兼容入口
零值 setter：缺少来源身份，无法安全处理重叠状态
状态移除：仍需状态系统按剩余来源重算
```

### 11.2 getter 可以做到真正的最小迁移

推荐的读取语义是让公开属性继续返回剩余毫秒数，而不是返回绝对时间戳：

```ts
private _is_busy_ts = 0;

get is_busy(): number {
    return Math.max(0, this._is_busy_ts - Date.now());
}
```

这样现有两类用法都成立：

```ts
if (me.is_busy) { ... }                              // 剩余时间大于 0 即为 true
this.call_out(this.auto_attack.bind(this), me.is_busy); // 得到剩余毫秒数
```

仓库中 `is_*` 的读取点很多，而把它们都改成 `has_effect()` / `effect_remaining()` 会产生较大的机械改动。getter 把时间换算集中在框架内部，确实是当前代码结构下最小且自然的兼容方式。

它还有一个明显好处：即使状态定时器有少量延迟，只要时间已到，getter 也会立即返回 `0`，不会因回调尚未运行而继续生效。

### 11.3 正数 setter 的合理语义

为了兼容现有 `me.is_busy = duration`，正数 setter 可以解释为“从现在起至少再生效 duration 毫秒”：

```ts
set is_busy(duration: number) {
    if (duration > 0) {
        this._is_busy_ts = Math.max(
            this._is_busy_ts,
            Date.now() + duration,
        );
    }
}
```

这能正确处理自然重叠：较短来源不会覆盖较长来源，较长来源会延长角色状态。类似现有代码：

```ts
if (me.is_rash < 8000) me.is_rash = 8000;
```

在 getter 返回剩余时间、setter 接收持续时间的约定下也仍然成立。

不过要明确，这个 setter 的语义是 `extend`，不是普通的 `set`。从 API 命名和可读性上，显式的 `extend_effect(key, duration)` 更准确；保留 setter 主要是为了兼容旧代码。

### 11.4 `is_xxx = 0` 是该方案的关键缺口

setter 只收到数值 `0`，JavaScript/TypeScript 不会把调用者或对应 buff 一并传入。框架无法知道这次清理属于 A、B，还是要求强制清除全部来源。

假设：

```text
A 到 10:00:10
B 到 10:00:20
角色 _busy_ts = 10:00:20
```

当 A 执行 `is_busy = 0`：

- 若 setter 直接清零，会错误清除 B；
- 若 setter 忽略清零，A 被提前驱散时可能继续生效；
- 若 setter 只在 `_busy_ts <= now` 时清零，能处理自然到期，但无法处理 B 在 `10:00:05` 被提前驱散后恢复 A；
- 若 setter 尝试“比较时间戳”，它仍没有 A 或 B 自身的时间戳可供比较。

因此，单参数 setter 无法同时满足“重叠安全”和“允许按来源提前取消”。这是信息不足，不是 setter 内部判断技巧可以补上的。

### 11.5 还有两个容易遗漏的反例

#### 刷新为更短时间

`override: 2` 替换状态时，新状态可能因数值、来源或减免变化而比旧状态更短。只做：

```text
_xxx_ts = max(_xxx_ts, newEndAt)
```

会残留旧状态较晚的结束时间，导致新状态已经结束但角色仍受影响。刷新/替换必须移除旧贡献后，从当前状态重新解析，而不能只调用“延长型 setter”。

#### 当前最长来源被提前清除

当最长来源提前被驱散时，正确结果可能不是 `0`，而是恢复到第二长来源的结束时间。单个 `_xxx_ts` 只保存最大值，没有保存第二大值；必须扫描剩余 `status[]`，或维护来源索引。

### 11.6 最小且正确的组合方案

建议保留你的 getter 思路，但把 setter 限定为兼容入口，生命周期系统使用内部方法：

```ts
private _is_busy_ts = 0;

get is_busy(): number {
    return Math.max(0, this._is_busy_ts - Date.now());
}

/** 兼容旧代码：只允许延长，不负责按来源撤销 */
set is_busy(duration: number) {
    if (duration > 0) this.extend_effect('busy', duration);
    else this.clear_legacy_effect('busy'); // 仅处理明确的旧式独占来源
}
```

状态系统本身不要通过公开 setter 添加和删除，而应使用：

```text
attach_status_effect(status, key, endAt)
detach_status_effect(status, key)
recompute_effect_end_at(key)
```

最小实现不必维护复杂 token map，因为 `status[]` 已经包含来源：

```text
添加状态
  -> 状态保存 expireAt
  -> _xxx_ts = max(_xxx_ts, expireAt)

移除状态
  -> 先从 status[] 排除该状态
  -> 若该状态 expireAt < _xxx_ts，无需处理
  -> 否则扫描剩余 status[]，重算该 key 的最大 expireAt
```

这样得到的职责边界比较清晰：

```text
getter          负责把内部时间戳转换成兼容的剩余毫秒
setter          负责兼容旧式“延长”写法
状态生命周期方法 负责带来源地添加、刷新和移除
status[]        负责保存可恢复的来源事实
_xxx_ts         只是最大结束时间缓存
```

### 11.7 是否需要保留 public setter

从长期设计看，最好最终取消 public setter，改为只读 getter，并把直接赋值迁移为显式接口或隐藏状态。因为：

- 属性赋值看起来像覆盖，实际却是 `max` 延长，语义有些隐蔽；
- `= 0` 无法表达“取消自己”还是“强制清除所有来源”；
- setter 无法携带 source token；
- 直接赋值绕过状态实例的 UI、驱散、战斗清理和回调语义。

但在第一阶段保留 setter，能显著降低迁移量。仓库当前除了 `change_buff()` 外，仍有多处技能和地图代码直接写 `is_busy` / `is_rash`，一次性全部迁移的风险会高于先建立兼容层。

### 11.8 最终评价

你的方案中，**外置 `is_*` 改成返回剩余时间的 getter，是目前最小且很优雅的读取兼容方案**。内部 `_xxx_ts` 统一保存绝对结束时间，也优于继续保存 duration。

但“setter 比较时间戳”只能安全表达新增或延长，无法单独表达带来源的结束。完整而仍然很小的方案应是：

```text
getter/setter 兼容外部旧接口
+ 状态自身 expireAt
+ 移除最长来源时扫描 status[] 重算
```

所以它可以成为推荐实现的外层形式，但不能让 setter 取代状态来源管理。若把状态增删留在内部生命周期接口中，这一组合在当前项目里比全量贡献堆更小，也足够优雅和正确。

## 12. 用显式 `xxx_end(end_ts)` 替代 `is_xxx = 0` 能否闭环

### 12.1 简短结论

这个改进比把 `0` 交给 setter 明确得多，但仅有：

```text
正数 setter + 单个 _xxx_ts + xxx_end(end_ts)
```

仍不能覆盖当前系统的全部生命周期。它能完美处理“所有来源都只在自己的计划结束时自然结束”的情况；一旦允许提前驱散、技能提前中止或相同结束时间来源碰撞，就还需要保留来源集合，或在结束当前最大来源时扫描事实源。

如果把接口稍微调整为：

```text
token = xxx_begin(duration)
xxx_end(token)
```

并由框架保存活动 token，这就能形成一个最小而完整的闭环。token 可以携带 `end_ts`，但不应只依赖调用方自行计算的时间戳。

### 12.2 只比较 `end_ts` 能正确处理什么

若 A、B 都只自然结束：

```text
A.end_ts = 10:00:10
B.end_ts = 10:00:20
_xxx_ts = 10:00:20
```

A 调用 `xxx_end(10:00:10)` 时发现它不是当前最大值，可以忽略；B 到 `10:00:20` 结束时，A 也必然已经结束，此时把缓存清零是正确的。

因此在以下严格前提下，单最大时间戳确实足够：

- 所有来源从“现在”开始生效；
- 每个来源只在自己的 `end_ts` 到达后结束；
- 不存在提前取消；
- 刷新不会缩短原来源；
- 永久效果另有定义。

### 12.3 提前结束时仍然缺少次长来源

当前项目不满足上述前提。状态可以被驱散、战斗结束清理，连招也可能因没有敌人而提前停止：

```text
A.end_ts = 10:00:10
B.end_ts = 10:00:20（当前最大值）
B 在 10:00:05 调用 xxx_end(10:00:20)
```

框架虽然能确认 B 的 `end_ts` 等于 `_xxx_ts`，却不知道应该恢复 A 的 `10:00:10`，因为单个 `_xxx_ts` 已丢失次大值：

- 直接清零：错误清除仍生效的 A；
- 保持 `10:00:20`：产生已经结束的 B 的幽灵效果；
- 改为当前时间：仍错误清除 A。

所以 `xxx_end(end_ts)` 解决了“结束者声明自己原计划到何时”的问题，却没有解决“剩余来源有哪些”的问题。

### 12.4 相同时间戳不能唯一标识来源

两个状态可能拥有同一个 `end_ts`，特别是在同一逻辑帧批量施加、时间被取整，或多个效果共用一个持续时间时：

```text
A.end_ts = T
B.end_ts = T
_xxx_ts = T
```

A 在 T 之前被提前移除并调用 `xxx_end(T)` 时，不能清零，因为 B 仍有效。仅比较时间戳无法区分 A 和 B。

如果结束只发生在 T 到达以后，这个碰撞无害，因为两者都已经自然失效；但当前系统允许提前结束，因此要么扫描剩余来源，要么在内部为相同时间戳维护引用计数/独立 token。

### 12.5 只保存 `start_time` 还不够

状态保存 `start_time` 后，可以计算：

```text
end_ts = start_time + duration
```

但前提是这个 `start_time` 必须也是框架登记效果时使用的同一时刻。若代码是：

```ts
buff.start_time = Date.now();
me.is_busy = buff.duration; // setter 内再次 Date.now()
```

两个时间可能相差若干毫秒：

```text
状态计算的 end_ts = 第一次 now + duration
setter 保存的 _ts   = 第二次 now + duration
```

结束时做精确比较会匹配失败。使用 `>=` 或容差比较又会引入来源误判，不能作为可靠修复。

因此必须由同一个开始操作生成时间戳，并把框架实际登记的值保存在状态上。状态字段应直接保存 `effect_end_ts` 或 token；`start_time` 仍可用于 UI，但不应事后用来猜测登记值。

### 12.6 setter 无法返回登记的时间戳

JavaScript 属性 setter 的返回值对赋值方不可见：

```ts
const token = (me.is_busy = duration);
```

这里 `token` 得到的是右侧的 `duration`，不是 setter 内部返回的 `end_ts`。因此若结束方需要保存精确 token，单靠赋值语法无法完成。

可选设计有三种：

1. 显式开始接口，推荐：

   ```ts
   const token = me.busy_begin(duration);
   me.busy_end(token);
   ```

2. 调用方先生成绝对时间，再把绝对时间交给 setter：

   ```ts
   const endTs = Date.now() + duration;
   me.is_busy = endTs;
   me.busy_end(endTs);
   ```

   这会让 getter 返回 duration、setter 却接收 timestamp，读写语义不对称，容易误用，不够优雅。

3. 状态系统绕过 public setter，内部调用 `attach_effect(status, key, endTs)`；setter 只兼容不需要提前取消的旧代码。

### 12.7 最小正确实现：时间戳 token 集合

若目标是让直接技能效果和 buff 都统一闭环，最小的数据结构不是复杂贡献堆，而是每类效果一个活动 token 集合：

```text
EffectToken
  id       唯一来源标识
  end_ts   计划结束时间
```

接口：

```ts
const token = me.effect_begin('busy', duration);
me.effect_end(token);
```

角色内部：

```text
Map<effectKey, Map<tokenId, end_ts>>
_xxx_ts = 当前集合中最大的 end_ts
```

行为：

- begin：登记 token，并用 `max` 更新 `_xxx_ts`；
- end：只删除自己的 token；
- 删除的不是最大来源：缓存不变；
- 删除的是最大来源：遍历该小集合恢复次大值；
- getter：返回 `max(0, _xxx_ts - now)`；
- 自然到期 token 可以在 end 时删除，也可在重算时惰性清理。

如果坚持只用 `end_ts` 本身作为 token，至少要使用 `Map<end_ts, count>` 处理同时间戳碰撞。但这仍无法区分同结束时间来源中的某个刷新或重复结束；增加一个递增 id 的成本很低，语义更可靠。

### 12.8 更贴近当前状态系统的更小变体

如果本轮只修复 `add_status()` 管理的效果，而暂不统一直接技能赋值，可以不建立通用 token 集合：

```text
状态保存精确 effect_end_ts
status[] 充当来源集合
xxx_end(status.effect_end_ts) 命中当前最大值时扫描剩余 status[]
```

但结束接口必须知道待删除状态已经从扫描集合排除，或者接收状态实例以便跳过它。只传 `end_ts` 在相同时间戳情况下无法指出应该排除哪一个，因此更稳妥的是：

```text
status_effect_end(status, effectKey)
```

直接技能中的临时效果仍需迁移为隐藏状态或 token API，否则它们与 `status[]` 中的来源无法互相恢复。

### 12.9 最终判断

把 `is_xxx = 0` 改成 `xxx_end(end_ts)`，使结束动作从“无条件清零”升级为“带原结束信息的条件释放”，方向是正确的，也能修复最常见的自然到期覆盖问题。

但要形成无漏洞的最小闭环，还需满足以下二选一：

```text
方案 A：xxx_begin(duration) 返回唯一 token，xxx_end(token)，框架保存活动 token 集合

方案 B：状态保存框架生成的精确 end_ts，结束当前最大来源时扫描排除该实例后的 status[]；
       所有非状态来源迁移成隐藏状态
```

其中 A 对当前仍存在的直接技能效果更通用，修改点也更机械；B 对 `add_status()` 内部改动更小。单纯依赖“状态保存 start_time，再用 start_time + duration 传给 end”存在时钟不一致和来源碰撞，不能算完整闭环。

## 13. 内部到期时间戳 + 返回管理凭证 + 状态/闭包持有

### 13.1 是否是当前最简易且安全的方案

是，但需要把表述修正为：

```text
公开 getter 兼容读取
+ 显式 begin 方法登记来源并返回管理凭证
+ 状态实例或闭包持有凭证
+ 显式 end 方法只释放该凭证
+ 框架内部保存活动凭证并缓存最大 endAt
```

这是当前代码结构下兼顾修改量、正确性和可读性的推荐方案。它不需要完整的堆或复杂状态实例框架，同时能统一 `status[]` 状态和技能闭包产生的临时 `is_*` 效果。

需要强调：不能使用真正的 JavaScript 属性 setter 来“返回管理时间戳”。属性 setter 的返回值不会成为赋值表达式的结果，因此开始操作必须是普通方法。

### 13.2 推荐接口

```ts
interface EffectToken {
    readonly id: number;
    readonly key: EffectKey;
    readonly endAt: number;
}

get is_busy(): number {
    return Math.max(0, this._busyEndAt - Date.now());
}

const token = me.begin_effect('busy', duration);
me.end_effect(token);
```

对于状态：

```ts
buff.busyToken = me.begin_effect('busy', buff.duration);
// 状态结束
me.end_effect(buff.busyToken);
```

对于闭包：

```ts
const rashToken = me.begin_effect('rash', duration);
me.call_interval(..., () => me.end_effect(rashToken));
```

这样开始和结束共享框架生成的同一个凭证，不依赖调用方再次调用 `Date.now()`，也不需要从 `start_time + duration` 反推结束时间。

### 13.3 为什么凭证不应只是裸时间戳

`endAt` 是凭证的重要数据，但不适合作为唯一身份：

- 两个来源可能在同一毫秒结束；
- 同一来源可能刷新并产生新生命周期；
- 旧闭包可能重复执行结束回调；
- 仅凭相同 `endAt` 无法判断应删除哪个来源。

因此推荐返回 `{ id, key, endAt }`，或者内部不可伪造的对象引用。`id` 保证来源唯一，`endAt` 用于排序和更新最大缓存。

若极端追求字段最少，也可以把框架生成的单调递增 id 与 `endAt` 分开保存；不建议通过不断给时间戳加 1 来制造唯一性，因为那会让结束时间与真实语义发生偏移。

### 13.4 框架为什么仍需保存活动凭证

仅让状态或闭包保存 token，而角色只保存 `_busyEndAt`，仍无法恢复提前结束的次长来源：

```text
A.endAt = 10 秒
B.endAt = 20 秒
B 在第 5 秒提前 end
```

框架必须知道 A 仍然存在。因此角色内部至少需要：

```text
Map<EffectKey, Map<TokenId, EffectToken>>
```

这不是重复保存业务状态，而是很小的效果租约表。它的职责只有来源身份和结束时间，不负责 UI、属性、回调或 buff 叠层。

常规路径成本：

- begin：登记 token，并以 `max` 更新缓存，O(1)；
- end 非最大来源：删除 token，O(1)；
- end 最大来源：扫描该 effect 的剩余 token，恢复最大值，O(k)；
- getter：从最大缓存计算剩余时间，O(1)。

由于单个角色的同类控制来源通常很少，扫描小 Map 比引入最大堆更简单，也足够高效。

### 13.5 状态刷新和旧闭包安全

刷新时不能修改旧 token 后继续复用。更清晰的流程是：

```text
结束旧 token
-> 创建新 token
-> 把新 token 附着到当前状态实例
```

如果旧定时器稍后触发并再次执行 `end_effect(oldToken)`，框架发现 token id 已不存在，直接幂等返回，不会删除新 token。

状态替换时，可以先登记新 token，再结束旧 token，以避免更新过程出现瞬时空窗。由于 JavaScript 当前执行栈内没有其他代码并发观察，中间顺序通常不会外泄，但统一采用“先新后旧”更稳妥。

### 13.6 自然到期与清理策略

getter 应始终以时间判断为准：

```ts
Math.max(0, cachedEndAt - Date.now())
```

即使定时器延迟，效果也不会超时生效。到期 token 的 Map 清理可以采用：

- 原状态/闭包到期时主动 `end_effect(token)`；
- 在最大来源结束、创建新来源或批量清理时顺便删除过期 token；
- 必要时提供角色级统一清理，但无需为每次 getter 扫描 Map。

缓存中暂时存在已过期 token 不影响正确性，只影响少量内存；主动结束和惰性清理结合即可。

### 13.7 public setter 如何处理

如果希望第一阶段降低迁移量，可以暂时保留正数 setter：

```ts
set is_busy(duration: number) {
    this.begin_legacy_effect('busy', duration);
}
```

但这样调用方拿不到 token，也就无法安全提前结束。它只能用于确认会自然到期的旧代码。所有存在 `= 0`、提前退出或刷新逻辑的路径，应直接迁移为 `begin_effect/end_effect`。

长期推荐将 `is_*` 变成只读 getter，TypeScript 在编译期禁止新的裸赋值，避免再次产生无来源效果。

### 13.8 最终推荐

当前最小且安全的闭环是：

```text
内部：每类 effect 的活动 token Map + 最大 endAt 缓存
读取：is_* getter 返回剩余毫秒
开始：begin_effect(key, duration) 返回唯一 token
持有：buff 实例字段或技能闭包保存 token
结束：end_effect(token)，幂等且只释放自身
```

这个方案比“所有调用方查询时扫描 status[]”改动更集中，也能覆盖不在 `status[]` 中的技能闭包；比最大堆和完整贡献索引更轻；比裸结束时间戳安全地解决了同毫秒碰撞、提前取消、刷新和旧回调问题。

因此，如果“setter接口”泛指一个设置/登记方法，那么答案是肯定的；如果特指 `set is_busy(...)` 属性 setter，则它不能返回管理凭证，应改为显式 `begin_effect()` 方法。

## 14. 不使用 Map：小数组中每次剔除一个来源

### 14.1 结论

同类 `is_*` 来源数量通常只有几个，使用嵌套 `Map` 确实偏重。更符合当前项目规模的实现是：每类效果维护一个很小的租约数组，结束时只剔除传入的那个租约。

本节的小数组方案取代第 13 节中的活动 token Map，其他 getter、最大结束时间缓存和 begin/end 凭证设计保持不变。

```text
busyLeases: EffectLease[]
faintLeases: EffectLease[]
rashLeases: EffectLease[]
...
```

添加 O(1)，普通删除 O(n)，删除当前最大来源后重算 O(n)。由于 n 很小，这比 Map/堆更简单，内存布局和调试体验也更直接。

### 14.2 推荐使用对象引用，而不是只用裸时间戳

```ts
interface EffectLease {
    key: EffectKey;
    endAt: number;
    active: boolean;
}

begin_effect(key: EffectKey, duration: number): EffectLease {
    const lease = {
        key,
        endAt: Date.now() + duration,
        active: true,
    };
    this.effectLeases[key].push(lease);
    this.effectEndAt[key] = Math.max(this.effectEndAt[key], lease.endAt);
    return lease;
}
```

状态字段或闭包保存该对象引用。结束时按引用查找并只删除一个：

```ts
end_effect(lease: EffectLease): void {
    if (!lease.active) return;

    const leases = this.effectLeases[lease.key];
    const index = leases.indexOf(lease);
    if (index < 0) return;
    lease.active = false;
    leases.splice(index, 1);

    if (lease.endAt >= this.effectEndAt[lease.key]) {
        this.effectEndAt[lease.key] = maxEndAt(leases);
    }
}
```

这里的对象本身就是 token，不需要额外 id，也不需要 Map 查找。

### 14.3 为什么对象数组优于时间戳数组

若使用 `number[]`，确实也可以 `findIndex(endAt)` 后只 `splice` 一个，相同时间戳的多个来源不会被一次删光。但仍存在一个安全问题：

```text
A.endAt = T
B.endAt = T
A 的结束回调意外执行两次
```

第二次按时间戳查找会误删 B。对象引用配合 `active` 能让结束操作幂等；第二次结束 A 只会被忽略，不可能命中 B。

因此最小安全单元不是 `{id -> token}` Map，而是数组中的唯一对象引用。对象分配本身成本很低，而且状态/闭包本来就需要持有一个管理凭证。

### 14.4 最大时间戳缓存

getter 不需要遍历数组，仍只读取缓存：

```ts
get is_busy(): number {
    return Math.max(0, this._busyEndAt - Date.now());
}
```

规则如下：

- begin：追加租约并 `max` 更新缓存；
- end 非最大租约：数组剔除一个，缓存不变；
- end 最大租约：剔除后扫描剩余数组取最大值；
- 相同最大时间戳：扫描后自然仍得到相同值；
- 无剩余租约：最大值归零。

自然到期但尚未主动结束的旧租约，可以在 begin、最大来源 end 或角色批量清理时顺便过滤。getter 通过时间比较保证它们不会超时生效。

### 14.5 最终精简结构

如果不希望维护按 key 的通用容器，也可以直接为六个固定效果各放一个数组和一个缓存字段：

```text
_busyLeases[]   + _busyEndAt
_faintLeases[]  + _faintEndAt
_missLeases[]   + _missEndAt
_rashLeases[]   + _rashEndAt
_shadowLeases[] + _shadowEndAt
_controlLeases[] + _controlEndAt
```

再由通用的内部辅助函数操作数组，避免复制六套逻辑。

因此，“多来源每次剔除一个”是成立的，也比 Map 更适合当前规模。推荐最终方案收敛为：

```text
小数组保存唯一租约对象
+ 最大 endAt 缓存
+ getter 返回剩余时间
+ begin 返回租约对象
+ end 按对象引用剔除一个且保持幂等
```

这是比嵌套 Map 更轻，同时仍覆盖同时间戳、提前结束、重复回调和恢复次长来源的最小安全实现。

## 15. 进一步精简：单时间戳数组是否足够可靠

### 15.1 结论

可以。对当前 `is_*` 聚合语义而言，数组只保存 `endAt: number` 已经足够；相同时间戳的来源在效果解析上完全等价，结束时用 `findIndex()` 找到一个并 `splice(index, 1)` 即可。

但需要保证每个来源只成功执行一次结束。最轻量的保证方式不是租约对象，而是由 begin 返回一次性结束闭包：数组保存纯数字，闭包保存自己的 `endAt` 和 `ended` 标记。

### 15.2 最小实现

```ts
type EffectEnd = () => void;

begin_effect(key: EffectKey, duration: number): EffectEnd {
    const endAt = Date.now() + duration;
    const timestamps = this.effectTimestamps[key];
    timestamps.push(endAt);
    this.effectEndAt[key] = Math.max(this.effectEndAt[key], endAt);

    let ended = false;
    return () => {
        if (ended) return;
        ended = true;

        const index = timestamps.indexOf(endAt);
        if (index < 0) return;
        timestamps.splice(index, 1);

        if (endAt >= this.effectEndAt[key]) {
            this.effectEndAt[key] = maxEndAt(timestamps);
        }
    };
}
```

使用方式：

```ts
const endBusy = me.begin_effect('busy', duration);
// 自然结束、提前中止或清除时调用；重复调用无害
endBusy();
```

状态实例保存 `endBusy`，技能临时效果由原有回调闭包捕获 `endBusy`。

### 15.3 相同时间戳为什么不是问题

假设 A、B 同时结束：

```text
timestamps = [T, T]
```

A 的一次性闭包删除第一个 T，数组剩 `[T]`，聚合结束时间仍为 T；B 的闭包再删除剩余 T，聚合值归零。虽然数组没有标明哪个 T 属于 A，但两个 T 在业务上不可区分，删除任意一个都是等价的。

真正危险的是 A 的结束逻辑重复执行两次，从而把 B 的 T 一并删除。闭包内的 `ended` 保证第二次调用直接返回，因此不需要对象身份或额外 id。

### 15.4 状态只保存时间戳时的限制

如果 API 仍设计成：

```ts
const endAt = begin_effect(...);
end_effect(key, endAt);
```

那么调用者必须自行保证 `end_effect` 只调用一次。当前状态存在定时到期、驱散、战斗清理和旧回调等多条结束路径，这个约束容易被未来代码破坏。

可以给状态增加一个 `effect_ended` 标记来保证一次性，但这等于把闭包中的布尔值搬到状态对象上，并且一个状态同时携带多个 `is_*` 时需要分别标记。

因此更推荐：

```text
内部数组：只保存 number 时间戳
外部凭证：一次性 end 闭包
```

它没有租约对象，也没有 id/Map，同时保留幂等结束能力。

### 15.5 闭包分配是否比对象更轻

闭包本身也是一个对象，会有一次分配，因此不能从运行时内存角度断言它一定比 `{ endAt, active }` 更轻。它的优势主要是 API 更小：调用方只保存并执行一个函数，不可能传错 key 或 token。

如果极端关注分配数量，最省分配的是纯 `number[]` 加显式 `end_effect(key, endAt)`，但必须依赖严格的一次性结束约束。考虑当前来源数量极少，选择应优先看代码安全性，而不是单个小对象或闭包的理论开销。

### 15.6 最终推荐调整

推荐把第 14 节的租约对象进一步收敛为：

```text
每类 effect 一个 number[]
+ 最大 endAt 缓存
+ getter 返回剩余毫秒
+ begin_effect 返回一次性结束闭包
+ 状态或技能闭包保存该结束函数
```

如果项目能够在所有结束路径上严格证明“每个来源只调用一次”，则连一次性闭包也可以省掉，直接传 `endAt` 剔除一个。但从长期维护安全性看，数组存单时间戳、闭包提供幂等性，是目前最简洁且足够可靠的折中。

## 16. V8 对固定 number 类型时间戳数组的优化

### 16.1 会得到专用数字数组优化

会。V8 会根据数组实际存放的元素维护 elements kind。当前毫秒时间戳约为 `1.8e12`，超出 SMI 小整数的常见表示范围，因此只保存这类值的密集数组通常会进入 `PACKED_DOUBLE_ELEMENTS` 路径。V8 可以在专用 double backing store 中保存原始数字，不需要像普通对象元素那样为每个时间戳保存对象引用。

这使 `number[]` 很适合当前用途：

```text
连续存储
无租约对象字段
无 Map 节点和哈希结构
扫描最大值是简单的数字比较
GC 不需要逐个追踪时间戳对象
```

TypeScript 的 `number[]` 只提供编译期约束，真正触发优化的是运行时数组始终只收到有限数字。

### 16.2 应保持 packed double 形态

推荐只使用：

```ts
timestamps.push(endAt);
const index = timestamps.indexOf(endAt);
if (index >= 0) timestamps.splice(index, 1);
```

避免以下操作：

```ts
delete timestamps[index];       // 制造 hole
timestamps[largeIndex] = endAt; // 跳跃写入制造 hole
timestamps[index] = undefined;  // 混入非数字元素
timestamps.push({ endAt });     // 转成普通 object elements
timestamps.push(NaN);           // 虽仍是 double，但不符合生命周期语义
```

`splice(index, 1)` 会移动后续元素并保持数组密集，正适合来源数量很少的情况。数组一旦退化为 holey 或普通 object elements，V8 通常不会自动恢复到更专用的 elements kind，因此应从接口层确保只写入合法时间戳。

### 16.3 无需 TypedArray

`Float64Array` 的数字存储更加固定，但长度不可动态伸缩，也没有适合当前语义的 `push/splice`。为了删除一个来源，需要另外维护长度、移动数据或重新分配数组，复杂度得不偿失。

普通的 packed double `number[]` 已能获得主要收益，并保留最简单的增删接口，是这里更合适的选择。

### 16.4 性能结论

从 V8 表示方式看，单时间戳 `number[]` 确实比对象数组或 Map 更紧凑，也更容易走专用快速路径。最终建议的数据结构可以确定为：

```text
每类 is_* 一个密集 number[]
+ 一个最大 endAt 数字缓存
+ push 添加
+ indexOf + splice(1) 剔除单个来源
+ 删除最大来源时线性扫描重算
```

不过同类来源通常只有个位数，绝对运行时间本来就很小。选择该方案的首要收益仍是模型简单、分配少和生命周期逻辑直观；V8 的 packed double 优化是额外收益，无需围绕它做更复杂的微优化。

## 17. 稀有状态下的容器布局：懒 Map、懒对象还是固定字段

### 17.1 不要预建六个空数组或空 Map

考虑到多数角色在多数时间没有任何 `is_*` 来源，真正重要的是**整个容器懒创建**：

```ts
private _effectEnds?: EffectEnds;
```

无状态时保持 `undefined`；首次 begin 时才创建容器和对应 `number[]`；某类最后一个来源结束时删除该数组；容器完全为空后再次设为 `undefined`。

如果在构造角色时执行 `new Map()`，即使 Map 经常为空，也已经为每个角色分配了 Map 对象和内部状态，不会比一个 `undefined` 字段省内存。Map 的内存优势只有在它本身也被懒创建时才成立。

### 17.2 不需要“数组 + 独立 maxAt”两份状态

可以让每类时间戳数组保持升序，最后一个元素直接作为最大结束时间：

```ts
const ends = this._effectEnds?.busy;
const endAt = ends?.length ? ends[ends.length - 1] : 0;
return Math.max(0, endAt - Date.now());
```

新增来源通常发生在当前时刻，结束时间大多自然递增，常见路径直接 `push()`。当新结束时间小于末项时，再从尾部找到插入位置并 `splice()`。来源只有个位数，线性插入足够简单。

结束时：

```text
indexOf(endAt)
-> splice(index, 1)，只剔除一个
-> getter 读取新的末项
```

因此无需另存 `_busyEndAt` 等六个 max 缓存，也不需要在删除最大来源后额外扫描求最大值。排序数组本身同时承担来源集合和最大值索引。

### 17.3 Map 与普通对象的选择

只有六个固定 effect key 时，可用懒创建普通对象：

```ts
interface EffectEnds {
    busy?: number[];
    faint?: number[];
    miss?: number[];
    rash?: number[];
    shadow?: number[];
    control?: number[];
}
```

优点：

- 直接属性访问，代码简单；
- 不需要 Map 的哈希/表结构；
- key 是封闭集合，TypeScript 类型约束更直接；
- 整个对象仍可懒创建，空闲角色只保留 `_effectEnds === undefined`。

也可以使用懒 `Map<EffectKey, number[]>`：

- key 的增删接口统一；
- `map.size === 0` 很容易判断并释放整个容器；
- 以后 effect key 动态扩展更方便。

但不能仅凭“经常为空”断言 Map 一定比普通对象省内存；具体对象头和 backing store 大小取决于 Node/V8 版本，需要堆快照或基准测试才能定量。对于六个固定键，懒普通对象通常是更小、更直接的默认选择；Map 的主要优势是 API 和动态扩展，而不是必然的内存优势。

### 17.4 推荐的最终内存布局

```text
CHARACTER
  _effectEnds?: {
      busy?: number[]      // 有来源时才存在，升序
      faint?: number[]
      ...
  }
```

生命周期：

```text
无任何效果：_effectEnds === undefined
首次 begin：创建容器及该 key 的 number[]
继续 begin：有序插入 endAt
end：按 endAt 只 splice 一个
该 key 为空：删除该数组
全部 key 为空：_effectEnds = undefined
getter：读取对应数组末项并减 Date.now()
```

这个布局同时具备：

- 空闲角色只增加一个可选字段槽位；
- 活跃时只为实际出现的 effect 分配数字数组；
- 数组仍保持 packed double；
- 不需要六个数组、六个 maxAt 缓存或常驻 Map；
- getter 为 O(1)，begin/end 在极小数组上为 O(n)。

因此，如果 key 固定，推荐“**一个懒创建普通对象统合有序 number[]，数组末项兼任 maxAt**”；如果计划让 effect key 动态化，则换成同样懒创建的 Map。两者都应在完全清空后释放，Map 不是因为空而天然免费。

## 18. 生物实例键数量与 Hidden Class 影响

### 18.1 当前静态统计

按 TypeScript 类字段中带初始化器、并对继承链中的同名字段去重统计，当前主要生物实例的构造期唯一键数量约为：

| 实例类型 | 构造期初始化的唯一键 |
| --- | ---: |
| `CHARACTER` | 87 |
| `MONSTER` | 88 |
| `NPC` | 90 |
| `FOLLOWER` | 92 |
| `USER` | 108 |

其中 `CHARACTER` 自身声明了 87 个非 static 字段，68 个带初始化器；加上 `BASE`、`ITEM` 构造期初始化字段，并扣除子类重复覆盖的键后，普通 `CHARACTER` 实例约有 87 个稳定初始化键。

这不是运行时所有 own property 的绝对上限。以下路径还会按实例增加属性：

- `BASE.set()` 中的 `Object.assign(this, pars)`；
- 资源模板和任务逻辑动态注入字段或回调；
- `add_event()` 按事件名给实例安装方法；
- 部分声明为可选且没有初始化器的运行期字段。

因此实际 NPC 可能因模板不同具有不同 hidden class，静态统计主要用于比较方案前后的稳定基线。

### 18.2 统合六个 `is_*` 的键数量收益

当前六个字段都会在 `CHARACTER` 构造期间初始化：

```text
is_busy
is_faint
ig_control
is_miss
is_rash
is_shadow
```

若改成原型 getter，并用一个实例字段承载懒容器：

```ts
private _effectEnds: EffectEnds | undefined = undefined;
```

getter 定义在 prototype 上，不占每个实例的 own property；六个数据字段替换为一个 `_effectEnds`，净减少 5 个稳定实例键：

| 实例类型 | 当前 | 统合后估算 | 减少 |
| --- | ---: | ---: | ---: |
| `CHARACTER` | 87 | 82 | 5 |
| `MONSTER` | 88 | 83 | 5 |
| `NPC` | 90 | 85 | 5 |
| `FOLLOWER` | 92 | 87 | 5 |
| `USER` | 108 | 103 | 5 |

这个减少会降低每个实例的字段/属性 backing store 压力，也减少 hidden class descriptor 需要描述的字段。角色数量较多时，它是有意义的结构性收益。

### 18.3 `_effectEnds` 应在构造期初始化为 `undefined`

为了 hidden class 稳定，不建议只写一个不会产生运行时代码的 TypeScript 可选声明，再在首次状态出现时才给角色新增 `_effectEnds` 属性：

```ts
// 可能只存在于类型系统，取决于编译配置
private _effectEnds?: EffectEnds;
```

当前项目目标为 ES2020，类字段会经编译处理。最稳妥的写法是显式初始化：

```ts
private _effectEnds: EffectEnds | undefined = undefined;
```

这样所有角色在构造期按相同顺序拥有该字段，后续只改变字段值，不改变 `CHARACTER` 实例的属性集合，也就不会因首次中状态而产生一条新的 hidden class 分支。

全部效果清空时应执行：

```ts
this._effectEnds = undefined;
```

不要 `delete this._effectEnds`。删除角色自身属性会改变对象形状，频繁增删还可能促使属性存储转为 dictionary/slow properties。

### 18.4 嵌套容器隔离动态键变化

统合后的 effect key 增删只发生在 `_effectEnds` 指向的内部容器中：

```text
CHARACTER 的形状始终包含一个 _effectEnds 槽位
内部对象按需出现 busy/faint/... 键
```

因此即使内部普通对象因 `delete ends.busy` 发生 shape 转换，也不会改变外层 `CHARACTER` 的 hidden class。高频访问的 `me.is_busy` getter 首先读取稳定的 `_effectEnds` 字段，再访问很小的内部容器。

如果希望连内部容器也完全避免动态命名属性形状，可以用固定下标数组：

```text
_effectEnds?: Array<number[] | undefined>
busy=0, faint=1, control=2, miss=3, rash=4, shadow=5
```

但该外层数组会是对象元素数组，并不一定比六键小对象更省；可读性也更差。内部容器稀有且很小，无需为了 hidden class 再做这一层微优化。

### 18.5 是否能防止未来 hidden class 退化

能降低风险，但不能保证永不退化。

V8 的关键行为是：

- 相同属性和相同添加顺序的实例可以共享 hidden class；
- 构造后添加不同属性会产生 shape 分支；
- in-object 槽位用尽后，额外属性仍可保存在 fast property backing store，不等于立刻退化；
- 大量、反复或顺序不一致的属性增删更容易转为 dictionary/slow properties。

因此不存在一个可依赖的固定阈值，例如“第 100 个属性必然退化”。具体 in-object property 数量、slack tracking 和转 dictionary 的启发式会随 V8 版本及构造模式变化。

六并一的价值在于：

1. 稳定键净减少 5 个，为未来字段留出更多空间；
2. 稀有状态数据不再为每个实例长期占六个值槽；
3. 后续新增同类效果只增加内部容器 key，不再增加 `CHARACTER` own property；
4. getter 留在 prototype，外层角色形状更稳定。

但当前更大的 hidden class 风险仍来自 `Object.assign(this, pars)`、资源实例动态字段和按事件名安装/删除实例方法。若未来要系统治理对象形状，应优先把这些开放式动态属性收敛进 `_runtime`、`_events` 等稳定容器，而不是只依赖减少五个字段。

### 18.6 最终判断

综合键数量和 V8 对象布局，统合 `is_*` 不仅解决生命周期问题，也有合理的对象形状收益。推荐最终布局：

```text
prototype：六个只读 getter
CHARACTER own property：一个构造期初始化为 undefined 的 _effectEnds
活动数据：_effectEnds 内按需创建的有序 number[]
清空：字段值恢复 undefined，不删除 CHARACTER 字段
```

它把稳定键从六个降为一个，并将未来同类状态扩展隔离到内部容器。这个优化值得做，但应描述为“降低实例尺寸和 shape 压力”，而不是“确保不会发生 hidden class 退化”。

## 19. 字段收敛候选与退化为 dictionary properties 的风险

### 19.1 先区分三种“多”

当前生物字段看起来很多，但它们对 V8 的影响并不相同：

1. **构造期稳定字段多**：所有同类实例按相同顺序初始化，hidden class 可以共享；in-object 空间不足后会进入 fast property backing store，不等于立即退化。
2. **常驻子对象多**：例如每个实例都 `new Map()` / `[]`，即使不用也产生堆分配和 GC 压力。
3. **运行期动态键多且顺序不同**：不同 NPC 经 `Object.assign`、事件安装和资源注入得到不同字段，这是 shape 分叉和 dictionary/slow properties 的主要风险。

当前约 87～108 个稳定初始化键偏多，值得治理，但“键总数”并不是唯一甚至不是最危险指标。相比把十个热标量塞进一个对象，减少常驻空容器和隔离动态键通常收益更大。

### 19.2 应保留为直接字段的热数据

以下字段处于战斗、移动、消息和属性计算热路径，建议继续作为直接字段：

```text
hp/max_hp/mp/max_mp
fight_type/enemy/release_time/attack_handler
gjsd/ds/gj/fy/mz/zj/bj
diff_sh_per/diff_fy_per
skills/status/equipment
environment/socket
```

把它们收敛成：

```ts
this.combat.gj
this.vitals.hp
```

虽能减少外层键，却给每次访问增加子对象加载，并要求大范围修改资源代码。V8 可以优化稳定访问链，但不能假设所有动态资源路径都能内联；这类迁移的风险和改动量高于可能获得的对象槽位收益。

因此不要以“字段越少越好”为目标。外层保留几十个稳定热字段是合理的。

### 19.3 第一优先级：收敛常驻但稀有的子系统分配

#### BASE 临时数据

当前 `BASE` 为所有游戏对象常驻创建：

```ts
_temp_values: Map<string, any> = new Map();
_temp_expiry: Map<string, number> = new Map();
```

临时数据调用虽然很多，但并非每个物品、房间和生物实例都一定持有临时值。可以收敛为一个构造期稳定但内容懒创建的字段：

```ts
_tempStore: {
    values: Map<string, unknown>;
    expiry?: Map<string, number>;
} | undefined = undefined;
```

收益：

- 两个实例键变一个；
- 无 temp 的对象不再分配两张空 Map；
- expiry 只在首次设置有时限值时创建；
- 动态 temp key 已被隔离在 Map 中，不影响宿主 hidden class。

这是比继续压缩 `CHARACTER` 热字段更有潜力的全局优化，但涉及约 1500 处 temp 调用背后的公共实现，必须以 API 不变、内部替换为原则。

#### 技能冷却 `pfm_cd`

当前每个 `CHARACTER` 都执行：

```ts
pfm_cd: Map<string, number> = new Map();
```

若大量普通 NPC 从未产生独立技能冷却，可保留一个稳定字段但把值改为 `undefined`，首次写入时才创建 Map：

```ts
pfm_cd: Map<string, number> | undefined = undefined;
```

它不减少键数，但避免闲置 Map 分配。是否值得需要统计实服中使用独立 CD 的角色比例；代码层面属于低风险候选。

#### NPC 商店操作

`shop_actions = []` 会为每个 NPC 分配数组，而只有商店 NPC 使用。改为 `shop_actions?: ...[]` 并在 `set_goods`/注册操作时懒创建，可省分配，但字段声明若不显式初始化不会成为稳定 own key。使用方需统一处理 `undefined`。

这类“一字段一空数组”的收益小于 temp 双 Map，但改动也较局部。

### 19.4 第二优先级：收敛同生命周期、同访问域的冷字段

以下字段可以按子系统分组，但应在明确做内存治理时实施，不必夹带在状态修复中：

#### 伤害统计子系统

```text
damages
record_damage
_damage_registered
sum_damages
```

可变为一个懒 `_damageStats`。大多数非统计角色只保留一个 `undefined` 字段，开启统计时再创建。该组内部生命周期一致，外部直接访问点相对可控，是较好的收敛对象。

#### 自动战斗缓存

```text
auto_skills
attack_count
busy_pfm
pfm_rate
auto_pfm
```

其中 `auto_pfm` 和部分判定较热，未必适合全部嵌套；可只把三个稀有缓存/计数放进 `_autoCombat`，保留 `auto_pfm` 直接字段。不要为了形式整齐强行整组迁移。

#### 跟随/组队关系

```text
follow_target
follow_targets
team
master
listener（随从）
```

语义相关但类型跨度大，而且移动路径频繁读取 `follow_target/team`。除非堆快照显示它们占用显著，否则优先级低于 temp、状态和动态 NPC 元数据。

#### USER 网络/通知缓存

```text
_notify_markers
_notify_frames
direct_send
request_count
disconnect_time
```

两个通知数组是高吞吐优化的并行数组，贸然嵌套会增加热路径间接访问。更值得考虑的是把两数组作为一个可选 `_notifyBuffer` 懒创建，但需要实际广播基准和堆快照支撑，不能仅凭字段数量修改。

### 19.5 最高 shape 风险：NPC 稀有动态元数据

`NPC` 类型中声明了大量按玩法注入的可选字段：

```text
diff_level/pfm_rate/is_dasong/is_menggubing/gate_index/iswall
boss_index/min_fbindex/event_id/no_alloc/drops_count/user_items
is_party_boss/top_index/auto_eqs/attack_count
battle_grade/battle_role/battle_death_handled
```

没有初始化器的 TypeScript 可选声明本身通常不产生实例键；真正的问题是不同资源在运行期以不同组合和顺序写入这些字段。这样会为 NPC 形成大量 hidden class 分支。

这组最适合收敛到一个稳定容器，例如：

```ts
runtime: Record<string, unknown> | undefined = undefined;
```

或者按主要玩法建立类型化小对象：

```ts
npc_runtime?: BattleRuntime | BossRuntime | XiangyangRuntime;
```

外层 NPC 只改变一个稳定槽位的值，玩法特有 shape 被隔离到生命周期更短、数量更少的内部对象。若字段只是临时值，也可以复用现有 `set_temp/query_temp`，但高频类型化访问不应全部退回字符串 Map。

这是减少 shape 多态性最值得做的方向，其优先级高于把稳定的 `hp/mp/gj` 收进大对象。

### 19.6 回调和事件动态安装的风险

资源对象可能通过 `Object.assign(this, pars)` 注入回调，`add_event()` 还会执行类似：

```ts
this[fname] = function (...) { ... };
// 移除时 delete this[fname]
```

添加不同命名属性会产生 hidden class 分支；频繁添加和删除命名属性是转为 dictionary/slow properties 的典型诱因。V8 进入 slow properties 后，属性元数据保存在实例自己的字典中，inline cache 的优化能力也会下降。

建议：

- 事件分发方法尽量保留在 prototype，只让 `_events` 容器动态变化；
- 避免给每个实例安装和删除不同名字的 wrapper 方法；
- 模板回调若名称集合固定，可在基类 prototype 提供分发入口，实例只在 `_callbacks` 容器保存函数；
- `Object.assign(this, pars)` 只用于稳定配置字段，开放式玩法元数据进入 `_runtime`。

注意：把所有东西塞进一个 JavaScript `Map` 并非免费。Map 适合真正动态的 key；固定字段放入 Map 会失去直接属性访问和类型清晰度。目标应是把**动态冷键**隔离，而不是把整个角色退化成手工 Map 对象模型。

### 19.7 退化风险分级

| 模式 | 风险 | 建议 |
| --- | --- | --- |
| 构造期按固定顺序初始化 80～100 个字段 | 中低 | 可保持 fast properties；关注实例尺寸和 backing store |
| 继承子类重复写父类已有字段 | 低 | 不新增键，主要是重复赋值成本 |
| 首次使用时给所有实例添加同一个字段 | 中 | 构造期预留为 `undefined`，保持 shape 一致 |
| 不同 NPC 添加不同可选字段组合 | 高 | 收敛到 `_runtime`/类型化玩法状态对象 |
| 频繁 `delete this.someField` | 高 | 字段保留并赋 `undefined`，或删除内部容器条目 |
| 动态安装/删除不同名字的实例方法 | 高 | 固定 prototype 入口 + `_events/_callbacks` 容器 |
| 固定热标量全部迁入 Map | 性能风险高 | 不建议；Map 只承载动态冷数据 |

### 19.8 推荐治理顺序

1. 本次状态修复先将六个 `is_*` 数据字段收敛成一个稳定 `_effectEnds`，净减 5 个键；
2. 将 NPC/任务的稀有动态字段逐步收进 `_runtime` 或类型化玩法对象，优先降低 shape 分叉；
3. 将 `BASE` 两张常驻 temp Map 改为一个懒 `_tempStore`，重点减少全局空容器分配；
4. 评估 `pfm_cd`、`shop_actions`、伤害统计等稀有子系统的懒创建；
5. 重构动态事件 wrapper，避免在宿主对象上反复添加/删除方法名；
6. 使用生产 Node 版本的 heap snapshot、`%DebugPrint`/专用基准验证实例尺寸和 fast/dictionary 状态，再决定是否继续收敛热字段。

### 19.9 最终结论

字段数量确实已经偏高，但当前不应进行一次“大对象分组”式全面重构。最合理的边界是：

```text
热、稳定、广泛读取的数据 -> 保持直接字段
冷、稀有、同生命周期的数据 -> 懒子对象
开放式动态玩法数据         -> _runtime / temp / 类型化运行时容器
固定接口、动态实现           -> prototype 入口 + 回调容器
```

六个 `is_*` 统合是很好的起点，因为它同时满足语义相关、稀有、可统一 getter、净减字段且迁移边界清晰。更大的退化风险来自 NPC 动态字段和实例方法增删，而不是稳定存在的战斗标量本身。
