# 状态生命周期问题

## 1. 问题概述

`busy`、`faint`、`rash`、`shadow`（以及同类的 `miss`、`ig_control`）目前采用“双挂载”模型：

1. buff 本身保存在角色的 `status[]` 中，按 `id` 管理生命周期、定时器、叠层和 UI 展示。
2. buff 的 `change_buff()` 同时把效果镜像到角色类字段，例如 `is_busy`、`is_faint`、`is_rash`、`is_shadow`。

角色类字段是单值，不能表达“哪些 buff 正在提供该效果”。因此不同 `id` 但相同 `is_*` 标记的状态会互相覆盖：

```text
添加 A（id=a, is_busy=true, 3 秒） -> is_busy=3000
添加 B（id=b, is_busy=true, 5 秒） -> is_busy=5000
A 到期并卸载                      -> is_busy=0
                                      但 B 仍在 status[] 中
```

最终表现为状态列表仍显示 B，但战斗和指令判断已经认为角色不 busy。相反，如果 B 先结束，也会错误地清除 A。

## 2. 当前代码流程与影响范围

主要流程位于 `server/core/char/character.ts`：

- `add_status()` 将状态按 `id` 放入 `status[]`，并注册 `remove_status(sid)` 定时器。
- `remove_status()` 找到指定 `id` 后调用 `change_buff(item, false, ...)`，随后从数组移除。
- `change_buff(item, true)` 直接写入角色类标记的持续时间。
- `change_buff(item, false)` 无条件将对应标记写成 `0`。

受影响的行为包括：

- `can_attack()`、自动攻击循环和技能释放限制；
- 招架、闪避、绝对命中等战斗判定；
- 普通指令的 `allow_busy` / `allow_faint` 检查；
- 批量清除、战斗结束清除、状态刷新和叠层状态；
- 仍存在的直接赋值路径（例如部分技能直接写 `me.is_rash = ...`），它们与 buff 托管没有来源关联。

特别需要注意：同一 `id` 的 `override: 1` 叠层在减少一层时也会先调用一次卸载逻辑，因此并非只有“不同 id”才会触发问题。

## 3. 方案评价标准

方案至少需要满足：

1. 每个状态来源独立结束，不得清除其他仍存活来源；
2. 同一 `id` 的叠层、刷新和替换语义保持一致；
3. 批量清除、战斗清除和异常结束不会留下错误镜像；
4. 角色字段的现有调用方尽量无需大规模改写；
5. 状态持续时间、减免、来源加成和定时器只有一个权威计算点；
6. 可测试，且能发现直接赋值绕过状态系统的路径。

## 4. 更推荐的长期方案：状态集合为唯一事实源

不要让单个 buff 在卸载时直接执行 `is_busy = 0`。`status[]` 应作为事实源，角色类字段只是由所有当前有效 buff 聚合出的兼容镜像。

### 4.1 聚合规则

为每个共享标记提供统一重算函数，例如 `sync_status_flags()`：

- 遍历当前仍在 `status[]` 中的 buff；
- 对声明了该标记的 buff 计算剩余时间；
- 取所有来源的最大剩余时间；
- 没有来源时才写 `0`。

如果保留现有数字字段，聚合结果仍应是“最长剩余时间”，而不是最后添加者的持续时间。建议给状态增加明确的 `expire_time`（或等价内部字段），避免通过 `start_time + duration` 猜测 `on_interval` 等特殊状态的结束时间。

### 4.2 生命周期调整

`change_buff()` 只负责该 buff 独占的副作用：属性、回调、消息和临时数据；共享 `is_*` 标记不在这里直接清零。状态数组完成添加、替换、叠层减少或批量删除后，统一调用一次 `sync_status_flags()`。

这样可以自然覆盖：

- 不同 id 的同类状态重叠；
- `override: 1` 剩余层数；
- `override: 2` 刷新替换；
- `clear_downside()`、`remove_statuses()`、`clear_combat_status()`；
- 同时存在 busy/faint/rash/shadow 的组合。

### 4.3 直接赋值迁移

有明确生命周期的 `me.is_rash = duration`、`target.is_busy = duration` 等代码应迁移为内部 buff。若不希望显示在客户端，可增加 `hidden/internal` 属性，而不是继续绕过状态系统。短期可保留兼容接口，但必须带来源 token，不能再裸写共享字段。

## 5. 对“托管退避/接管”方案的分析

提议：在一个 buff 接管角色类 `is` 状态前，调用判定函数，传入状态键和持续时间：

1. 如果不可接管，则删除自身的 `is` 标记；
2. 如果可接管，则删除所有 buff 的该 `is` 标记，由当前 buff 接管。

### 5.1 可取之处

- 改动集中在状态接管点，现有消费 `is_busy` 等字段的代码可以继续工作；
- 若产品语义明确要求“同一时刻只能有一个控制来源”，接管模型比简单清零更接近该语义；
- 可以把优先级、持续时间比较和刷新策略集中在一个判定函数中。

### 5.2 关键问题

该方案实际上改变了游戏语义：它不是修复“重叠状态”，而是把同类状态设计成“互斥、抢占”。如果 A 与 B 本应同时存在，接管时删除 A 的 `is` 标记会造成：

- A 仍留在 `status[]`，但其声明与实际效果不一致；
- A 到期时仍会触发回调、消息、属性卸载，生命周期和镜像脱钩；
- B 先结束时无法恢复 A，除非额外保存被接管栈并重新接管；
- `override: 1` 叠层、`override: 2` 替换、批量删除都需要维护复杂的接管关系；
- “删除所有 buff 的该 is 标记”会修改状态定义本身，导致状态对象被复用或再次叠加时出现脏数据；
- 直接赋值路径没有 buff 身份，仍然无法与接管判定统一；
- 定时器执行顺序可能产生短暂空窗：旧 buff 被摘标记后，新 buff 尚未完成接管，战斗线程可能观察到错误状态。

因此，如果“不可接管”时只是删除当前 buff 的 `is` 标记，状态列表会显示一个实际不生效的 buff；如果“可接管”时删除其他 buff 的标记，则必须实现可恢复的优先级栈，复杂度接近重新实现状态系统。

### 5.3 何时适合使用

接管模型只适合明确的互斥控制效果，例如“硬控槽位”或“同类效果只取最高级”，并且应定义：

- 优先级/比较规则（持续时间、来源等级或显式 priority）；
- 被抢占状态是否暂停、缩短、彻底移除；
- 当前接管者结束后是否恢复上一层；
- UI 是否展示所有候选状态，还是只展示生效状态；
- 外部直接赋值如何获得 token。

它不适合作为当前所有 `is_*` 标记的通用修复方案。

## 6. 折中方案：来源租约 + 聚合镜像

如果暂时不能把所有直接赋值迁移成 buff，可增加内部“状态租约”：

```text
attach_state(flag, sourceToken, duration)
detach_state(flag, sourceToken)
```

角色保存 `flag -> sourceToken -> expireTime`，对外仍提供 `is_*` 数字镜像，并按最长剩余时间聚合。普通 buff 和临时技能效果都通过租约接入，结束时只能释放自己的 token。

这是安全的过渡方案，但最终仍建议统一收敛到 `status[]`，避免同时维护 buff、租约和裸字段三套模型。

## 7. 建议落地顺序

1. 先补回归测试，复现不同 id 重叠和同 id 叠层提前清零；
2. 抽出 `sync_status_flags()`，先停止 `change_buff(false)` 的无条件清零；
3. 为状态记录明确 `expire_time`，统一处理刷新、叠层和 `on_interval`；
4. 将直接写 `is_*` 的技能迁移为内部 buff 或带 token 的租约；
5. 对确实需要互斥的效果，再在聚合层增加 `priority/stackingGroup`，不要用“删除其他 buff 的标记”实现隐式接管；
6. 增加状态生命周期、批量清除、战斗结束和并发定时器测试。

## 8. 结论

“托管退避/接管”可以作为特定互斥控制效果的策略，但不应作为所有 `is` 类状态的底层修复。更稳妥的基础设施是：**buff 保留自己的声明和生命周期，角色类状态由当前有效来源聚合计算；任何单个 buff 都无权直接清除共享状态。**

## 9. 兼顾性能与优雅性的最终方案

如果不考虑代码修改量，建议采用“状态实例 + 效果贡献索引 + 派生角色状态”的三层模型，而不是每次变更都扫描整个 `status[]`。

### 9.1 三层职责

```text
StatusInstance（状态实例）
  ├─ 生命周期、叠加、刷新、回调、UI 展示
  └─ instanceId 唯一，不再只依赖 sid 识别定时器

EffectContribution（效果贡献）
  ├─ instanceId / layerId
  ├─ effectKey：busy、faint、rash、shadow、miss、ig_control
  ├─ expireAt、priority、stackingGroup
  └─ active 标记

ResolvedState（角色派生状态）
  ├─ is_busy、is_faint 等现有兼容字段
  └─ 只读地由贡献索引解析得到
```

`status[]` 负责“有哪些状态以及如何展示”；控制效果查询走按 `effectKey` 建立的索引。角色的 `is_*` 字段不再由单个 buff 直接写入。

### 9.2 高性能索引

角色内部维护 `Map<effectKey, EffectBucket>`。每个 bucket 保存有效贡献，并维护按 `expireAt`（必要时再按 `priority`）排序的最大堆：

- 添加贡献：写入 token 并入堆，O(log n)；
- 移除贡献：只将 token 标记为 inactive，O(1)；
- 查询/重算：惰性弹出失效或过期 token，均摊 O(log n)；
- 读取 `is_busy` 等字段：读取缓存的 `ResolvedState`，O(1)。

当前控制来源通常很少，也可以使用“当前 winner + 备用堆”，只有 winner 失效时才选下一个来源。

### 9.3 解析策略

- `busy/faint/rash/shadow/miss/ig_control`：同类贡献默认取 `expireAt` 最大者，角色字段为其剩余时间；
- 不同 `effectKey` 互不影响；
- 需要互斥时，通过显式 `stackingGroup` 和 `priority` 选 winner；
- 被淘汰的贡献仍保持自己的生命周期，是否隐藏、暂停或移除由策略决定，不能通过篡改其他 buff 的 `is_*` 标记实现。

### 9.4 原子更新与定时器

每次状态变更在一个原子事务内完成：

```text
更新 StatusInstance
 -> 增删对应 EffectContribution
 -> 解析受影响的 effectKey
 -> 更新 ResolvedState
 -> 一次性发送状态/UI 增量
```

定时器回调必须携带 `instanceId/layerId`，不能只传 `sid`。回调先校验 token 是否仍 active，避免旧定时器在刷新或替换后误删新状态。多个字段同时变化时只重算受影响的 bucket，不做全角色、全状态扫描。

### 9.5 直接效果统一接入

原先直接写 `me.is_rash = duration` 的技能，也通过同一个 `EffectContribution` API 接入；不展示给客户端的效果使用 `internal` 标记。buff、技能临时控制、房间机制都拥有统一 source token，结束时只能释放自己的 token。

### 9.6 为什么优于“托管接管”

- 任一来源结束都不会误清其他来源；
- 不需要修改或删除其他 buff 的声明；
- 不需要维护隐式接管栈；
- 查询 O(1)，增删 O(log n) 或均摊 O(1)；
- 可以保留现有 `is_*` 数字字段，逐步迁移调用方；
- UI 状态和实际生效状态可以分别表达，不会出现列表与效果不一致。

这是在性能、可验证性和长期扩展性之间更平衡的底层方案。
