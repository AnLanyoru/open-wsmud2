# 副本编写指南

## 1. 适用范围

本文说明 `AREA.is_copy` 副本区域的编写与运行机制，重点解释房间原型、运行房间克隆、副本实例创建和清理。普通房间字段与回调请配合 [ROOM（房间）编写指南.md](ROOM（房间）编写指南.md) 阅读，区域配置请配合 [AREA（地区／副本）编写指南.md](AREA（地区／副本）编写指南.md) 阅读。

副本由两类资源共同组成：

- `server/res/area/` 下的 AREA 文件定义副本元数据、入口、房间路径前缀与地图。
- `server/res/map/` 下的 ROOM 文件定义每个房间的名称、出口、NPC、物品和回调。

## 2. 最小副本区域

```typescript
import { AREA } from '../../../core/room/area.js';

export default class extends AREA {
    id = 'example';
    name = '示例副本';
    desc = '用于展示副本结构。';
    is_copy = true;
    is_multi = false;
    is_diffi = false;
    expend = 10;
    exp = 1000;
    pot = 1000;
    first = 'fb/example/entrance';
    room_path = 'fb/example/';
    map = [
        { n: '入口', id: 'fb/example/entrance', p: [0, 0] },
        { n: '深处', id: 'fb/example/depths', p: [1, 0] },
    ];
}
```

关键约束：

- `is_copy = true` 才会按所有者创建独立房间实例。
- `room_path` 必须与副本全部房间的路径前缀完全一致，并以 `/` 结尾。
- `first` 必须指向入口房间；AREA 的清理流程依赖它。
- 当前 `ROOM.query_fb_first()` 和 `fb_*` 内部取的是 `area.rooms[0]`，并不会按 `AREA.first` 查找。如果资源加载后的 `rooms[0].path !== first`，这些辅助方法会定位到错误房间。应确保入口 ROOM 是该区域最先注册的房间，或避开这些辅助方法，改为通过 `WORLD.getRoom(area.first)?.query_copy(ownerId)` 明确取得入口克隆。
- `query_owner(me)` 决定实例隔离键。默认返回 `me.query_teamid()`；单人副本虽然通常也能使用默认逻辑，但需要按玩家永久隔离的区域应显式返回 `me.id`。
- `not_fb = true` 表示复制区域但不是会消失的常规副本，常用于住房、帮会等长期隔离空间。

## 3. 房间不是直接拿资源类当实例

当前 ROOM 使用“资源定义原型 → 基础运行房间 → 副本克隆”的模型。

### 3.1 首次加载

房间资源类实例化后，`ROOM.create(path)` 不会直接把该对象注册为玩家活动房间，而是：

1. 将资源定义对象保存到 `WORLD.ROOM_STORE`，作为干净原型。
2. 通过 `Object.create(原型)` 创建基础运行房间。
3. 调用 `on_clone()` 隔离可变状态并重放 NPC、物品生成记录。
4. 调用 `initBaseRoom(path)`，将基础运行房间注册到 `WORLD.ROOMS` 并关联 AREA。

因此：

- `WORLD.ROOM_STORE.get(path)` 是克隆来源，不应承载运行时玩家、战斗状态或副本进度。
- `WORLD.ROOMS.get(path)` / `WORLD.getRoom(path)` 返回基础运行房间。
- 副本区域的基础运行房间不会加入 `WORLD.RUN_ROOMS`；真正创建出的副本房间会加入。

### 3.2 为什么构造函数中的 NPC 和物品能出现在每个副本

`set_npc()` 与 `set_obj()` 会在定义阶段记录生成参数。每次 `ROOM.CREATE(path)` 克隆房间时，`on_clone()` 会重放这些记录，为新房间创建独立的 NPC 和物品实例。

```typescript
import { ROOM } from '../../../core/room/room.js';

export default class extends ROOM {
    name = '入口';
    desc = '一条通往深处的石道。';
    exits: Record<string, string> = {
        east: 'fb/example/depths',
    };

    constructor() {
        super();
        this.set_npc('example/guard');
        this.set_obj('example/token', 1);
    }
}
```

不要在模块顶层或共享对象中缓存运行 NPC；每个副本必须使用克隆后房间 `items` 中的实例。

## 4. 克隆时哪些状态会隔离

`ROOM.CREATE(path)` 从 `WORLD.ROOM_STORE` 取得干净原型，使用 `Object.create()` 创建房间并调用 `on_clone()`。克隆过程会为下列状态建立自有值：

- `items`
- `exits` 的浅拷贝
- temp 值与过期时间 Map
- 事件存储
- 批处理缓冲区、待发送列表和脏玩家集合
- 房间 JSON、出口 JSON、命令 JSON 缓存
- NPC 与物品生成记录对应的新实例

资源文件仍需遵守以下原则：

- 不要把可变运行状态写在模块级变量中。
- 不要在多个房间之间共享会被修改的数组、Map、Set 或普通对象。
- 新增 ROOM 可变引用字段时，应先确认克隆路径是否会为它创建自有副本；否则多个副本可能通过原型链共享状态。
- `on_create()` 会在基础运行房间和后续克隆房间创建时触发，不适合只执行一次的全局初始化。

## 5. 副本创建流程

通常由既有进入副本命令完成创建。底层流程如下：

```typescript
const area = AREA.Get('example');
const baseFirst = area?.first ? WORLD.getRoom(area.first) : undefined;
const copyFirst = baseFirst?.create_copy2(me, difficulty);
if (copyFirst) me.moveto(copyFirst);
```

`create_copy2(me, difficulty)` 会先调用 `area.query_owner(me)` 得到所有者 ID，再由 `create_copy(id, difficulty)` 递归处理区域及其子区域：

1. 对 AREA 的每个基础房间调用 `ROOM.CREATE(baseRoom.path)`。
2. 对所有区域克隆完成后，将难度写入入口克隆的 `diff` 标记。
3. 写入基础房间的 `copy_rooms[ownerId]`。
4. 写入克隆房间的 `owner`。
5. 对子区域递归执行同样操作。

创建完成后，可通过以下方法定位房间：

```typescript
const ownerId = area.query_owner(me);
const roomCopy = baseRoom.query_copy(ownerId);
const baseFirst = area.first ? WORLD.getRoom(area.first) : undefined;
const firstCopy = baseFirst?.query_copy(ownerId);
const currentCopy = baseRoom.query_copy2(me);
```

`query_fb_first(ownerId)` 当前等价于 `area.rooms[0].query_copy(ownerId)`，仅当 `rooms[0]` 就是 `AREA.first` 时才能安全使用。通用代码应按上例从 `AREA.first` 取得基础入口房间。

`query_copy2(me)` 在 `query_owner(me)` 返回空值时会返回基础房间本身，因此调用方若要求一定得到副本，应先验证 owner ID。

不要把副本克隆的 `path` 当作唯一实例 ID。克隆仍沿用资源路径，实例隔离依赖基础房间的 `copy_rooms[ownerId]` 与克隆的 `owner`。

## 6. 副本临时状态

ROOM 自身的 temp API 与 ITEM 一致：

```typescript
room.query_temp('boss_killed', false);
room.set_temp('boss_killed', true, 3600000);
room.add_temp('kill_count', 1);
room.remove_temp('boss_killed');
```

如果业务需要从任意副本房间访问“该队伍副本入口房间上的共享状态”，使用 `fb_*` 方法：

```typescript
this.fb_set_temp('boss_killed', true, me, 3600000);
const killed = this.fb_query_temp('boss_killed', me, false);
const count = this.fb_add_temp('kill_count', 1, me);
```

`fb_query_temp`、`fb_set_temp`、`fb_add_temp` 会定位 `AREA.first` 对应的入口克隆，再把数据存到入口克隆房间。从副本克隆调用时优先沿用当前房间的稳定 owner；从基础房间调用时使用 `AREA.query_owner(me)`。默认副本按队伍 ID 隔离，覆写 `query_owner()` 的副本会自动遵循自定义 owner 规则。

进入命令会在副本创建完成后把所选难度写入入口克隆的 `diff` 标记。运行期凡是带玩家上下文的难度分支，都应以该标记为唯一来源：

```typescript
const diff = this.fb_query_temp('diff', me, 0);
if (diff === 1) {
    // 困难模式逻辑
}
```

不要在资源房间中声明 `difficulty` 字段，也不要为单个副本另设 `*_difficulty` 临时标记。所有难度相关初始化和玩家交互都应读取入口上的 `diff`；需要在玩家首次进入房间时替换 NPC 或调整属性时，使用幂等的 `on_enter(me)` 逻辑。

## 7. 副本清理

推荐从 AREA 调用：

```typescript
area.clear_copy(me);
```

AREA 会根据 `first` 找到基础入口房间，再定位玩家对应的入口克隆并调用 `ROOM.clear_copy(me)`。

清理成立需要满足：

1. 当前入口克隆存在 `owner`。
2. `area.query_owner(me)` 与该克隆 `owner` 相同。
3. 若玩家有队伍，不能仍有其他队员停留在同一 AREA 且房间 owner 相同。

通过检查后，引擎会：

- 删除该玩家所有以 `fb/` 开头的 temp 键。
- 递归遍历 AREA 与子 AREA 的基础房间。
- 从 `WORLD.RUN_ROOMS` 移除每个 owner 对应的克隆。
- 调用克隆房间 `destroy()`，清空房间 `items` 并将 `owner` 置空。
- 删除每个基础房间的 `copy_rooms[ownerId]` 引用。

注意事项：

- 引擎没有按 `create_time` 或空房时长自动回收副本的机制。若完成、失败、掉线或中途退出路径没有显式调用清理，克隆会继续留在 `copy_rooms` 和 `WORLD.RUN_ROOMS` 中。
- `ROOM.destroy()` 本身只清空内容物与 owner，不负责从 `WORLD.RUN_ROOMS` 或基础房间 `copy_rooms` 移除引用；完整副本清理应走 `clear_copy()` / `clear_by_area()`。
- 清理前应先确保玩家已经离开待销毁副本。直接销毁仍有玩家的房间会清空 `items`，但不会替玩家选择新的 `environment`。
- ROOM 不托管业务定时器。房间中创建的 `setTimeout`、`setInterval` 或其他调度句柄不会被 `clear_copy()`、`clear_by_area()` 或 `destroy()` 自动取消；必须保存句柄，并在副本结束、失败、热更新重建等路径中由业务显式清理。
- 外部注册表、全局事件或不在房间 `items` 中的对象引用同样不会由房间清理自动释放，必须由业务自己的结束逻辑处理。

## 8. 房间热更新对现有副本的影响

ROOM 热更新会替换干净原型和基础运行房间。若旧基础房间已有 `copy_rooms`，引擎会为每个 owner 从新原型重新创建房间，并迁移玩家及其随从，然后销毁旧克隆。

这意味着：

- 新 NPC、物品、出口和房间定义会进入重建后的克隆。
- 普通 NPC、地面物品以及仅存放在旧房间 temp 中的运行状态不会自动迁移。
- 玩家与带 `master` 的随从会迁移到新房间。
- 不能依赖热更新保存副本战斗进度；需要保留的状态应明确迁移或让玩家重新进入副本。

## 9. 常见错误

### 9.1 在 AREA 上创建，随后按克隆 path 移动

错误原因是所有克隆共用资源 path，`WORLD.getRoom(path)` 只返回基础房间。应使用 `create_copy2()` 的返回值或 `query_copy()` 取得具体克隆对象，并把 ROOM 对象直接传给 `me.moveto(copyRoom)`。

### 9.2 手动设置 `is_copy_room` 或 `owner`

这两个值由克隆创建流程维护。只改字段不会建立 `copy_rooms` 映射，也不会递归创建完整区域。

### 9.3 把玩家参数传给 ROOM 的普通 temp API

ROOM 当前没有 `query_temp(name, me, def)` 这种覆写。按队伍入口共享状态应使用 `fb_query_temp`、`fb_set_temp`、`fb_add_temp`；当前房间自身状态使用继承自 ITEM 的普通 temp API。

### 9.4 直接调用 `destroy()` 代替清理副本

这会遗留 `WORLD.RUN_ROOMS` 和 `copy_rooms` 引用。完整清理必须走区域或房间的副本清理流程。

## 10. 检查清单

- AREA 已设置唯一 `id`、`is_copy = true`、正确的 `room_path` 与有效的 `first`。
- 每个 `map[].id` 与 ROOM 资源 path 一致。
- 所有出口目标都属于预期区域且可以反向返回或正常结束副本。
- `query_owner()` 的隔离策略与单人/组队设计一致。
- ROOM 构造函数只声明可重放的 NPC、物品和静态配置。
- 没有模块级可变状态泄漏到多个副本。
- 副本共享 temp 使用了与 owner 策略兼容的存储方式。
- 完成、失败、主动退出和掉线等结束路径都会先迁移玩家，再调用 `area.clear_copy(me)`；没有依赖引擎自动超时回收。
- 额外定时器、事件和外部引用有明确的业务清理逻辑，没有依赖 ROOM 托管。
- 已考虑房间热更新会重建现存克隆且只迁移玩家和随从。
