# 状态生命周期解决方案分档

## 1. 目标与现状判断

当前问题的根源不是某一个定时器提前执行，而是同一个效果存在两个事实源：

- `status[]` 按状态 `id` 保存状态、层数、定时器和 UI 信息；
- `is_busy`、`is_faint`、`is_miss`、`is_rash`、`is_shadow`、`ig_control` 等角色字段由每个状态直接写入和清零。

角色字段没有记录来源。只要两个不同状态贡献同一个字段，或者有状态效果与裸赋值效果重叠，任一来源结束时都可能错误清除其他仍有效的来源。同一 `id` 的 `override: 1` 状态在减少一层时，也会先执行 `change_buff(item, false, 1)`，因此同样会提前清零共享字段。

仓库内还存在 `me.is_rash = duration`、`target.is_busy = duration` 等非 `status[]` 管理路径。只修复 `remove_status()` 无法保证这些路径与状态路径重叠时的正确性。

下面将方案分成三个档次。三个档次不是简单的性能递进，而是事实源和生命周期统一程度的递进。

## 2. 方案对比

| 档次 | 核心做法 | 实施难度 | 覆盖范围 | 主要代价 |
| --- | --- | --- | --- | --- |
| 一：状态数组重算 | 状态变更后扫描 `status[]`，重算共享字段 | 低 | 正确处理受 `status[]` 管理的效果 | 裸赋值仍是例外；重算依赖状态时间信息准确 |
| 二：来源租约 | 每个状态和非状态效果都以 token 注册贡献，字段由贡献聚合 | 中高 | 覆盖当前所有共享效果来源 | 状态生命周期和效果租约仍是两套结构，需要严格配对 |
| 三：统一效果实例 | 状态与非状态效果共用一个生命周期内核，UI 状态只是可选表现 | 高，需要较大改造 | 统一当前及未来所有有时限效果 | 迁移范围大，需要分阶段兼容旧 API |

## 3. 第一档：状态数组重算

### 3.1 定位

这是最容易实施的止血方案。它优先保证 `add_status()` 管理的 busy、faint、miss、rash、shadow 和 ig_control 不再相互误清，保留现有角色字段及绝大多数调用方。

效果略差的含义是：它只能把 `status[]` 变成“有状态管理效果”的事实源，不能自然容纳技能中直接写角色字段的非状态效果。

### 3.2 实现方式

增加统一方法，例如：

```ts
sync_status_flags(changedKeys?: StatusFlag[]): void
```

重算规则如下：

1. 遍历变更完成后的 `status[]`；
2. 找出仍声明某个共享标记的有效状态；
3. 根据明确的 `expireAt` 计算每个来源的剩余时间；
4. 对同一标记取最大剩余时间；
5. 没有有效来源时才将对应角色字段设为 `0`。

`change_buff()` 继续处理属性、消息、`on_attach`、`on_expire` 和临时数据，但不再直接写入或清除上述共享字段。所有状态数组操作完成后再重算：

- 新增状态后；
- `override: 1` 增层或减层后；
- `override: 2` 替换完成后；
- `remove_status()` 删除完成后；
- `clear_downside()`、`clear_combat_status()`、`remove_statuses()`、`clear_status()` 批量修改完成后。

应给状态实例补充 `expireAt`。普通状态为最终到期时间；`on_interval` 状态应按剩余触发次数更新最终到期时间，不能只依赖最初的 `start_time + duration`。

### 3.3 非状态效果的兼容办法

短期保留裸赋值代码，但必须承认它不是完整解决方案。为了降低误清概率，可以先将已知裸赋值路径迁移成 `hidden/internal` 状态，或者在其清零前检查是否还有对应状态：

```ts
// 只能作为临时兼容，不能识别另一个裸赋值来源。
if (!has_status_flag('is_rash')) this.is_rash = 0;
```

这种检查只能避免非状态效果清掉可见状态，无法区分两个非状态效果，也无法在裸赋值结束后准确恢复较短或较长的其他来源。

### 3.4 优点

- 改动集中在 `character.ts` 的状态增删流程；
- `can_attack()`、指令限制和战斗判断等消费方无需改造；
- 状态数量通常很少，全量扫描成本可忽略；
- 能直接修复不同 `id` 重叠、同 `id` 叠层以及批量清除造成的提前清零。

### 3.5 缺点和适用边界

- 裸赋值仍然没有来源身份，不能保证与其他裸赋值或状态效果正确重叠；
- 状态字段与裸字段仍是双事实源；
- 若遗漏某个数组修改出口的重算，仍可能产生不一致；
- 数字字段代表的是一次快照式剩余时间，旧调用方若把它当绝对可靠的持续时间，语义仍不够清晰。

适合作为近期修复，或者系统暂时不准备迁移技能代码时采用。

## 4. 第二档：来源租约覆盖所有情况

### 4.1 定位

这一档以“每个来源只能释放自己”为基本原则，覆盖状态和非状态路径的所有共享标记冲突。它不要求立即重写整个状态系统，因此比第三档容易落地；但需要迁移所有直接赋值路径，实施量明显高于第一档。

### 4.2 数据结构与接口

角色内部维护按效果键分组的贡献表：

```ts
type EffectKey = 'busy' | 'faint' | 'miss' | 'rash' | 'shadow' | 'ig_control';

interface EffectLease {
    token: string;
    key: EffectKey;
    expireAt: number;
    active: boolean;
    ownerType: 'status' | 'skill' | 'system';
    ownerId?: string;
}
```

提供最小 API：

```ts
attach_effect(key, token, duration): void
refresh_effect(key, token, duration): void
detach_effect(key, token): void
query_effect_remaining(key): number
```

角色原有的 `is_*` 数字字段保留为兼容镜像，由租约表统一解析。默认规则是同一 `key` 取最大的 `expireAt`；只有租约表中已不存在有效来源时才返回或写入 `0`。

### 4.3 状态路径接入

每个运行中的状态必须有稳定的 `instanceId`，不能仅使用业务 `id` 作为 token：

```text
status:<instanceId>:busy
status:<instanceId>:rash
```

- 添加状态时注册其声明的全部效果租约；
- 刷新时只刷新该实例的租约；
- `override: 1` 可让整个状态实例持有一份租约，层数大于零时租约存在；若未来每层结束时间不同，则 token 细化到 `layerId`；
- 替换时先使旧实例 token 失效，再注册新实例 token；
- 删除、批量清理和战斗清理只能释放被删除实例自己的 token；
- 定时器回调携带并校验 `instanceId`，避免旧定时器删除同 `id` 的新实例。

### 4.4 非状态路径接入

所有直接赋值改为带 token 的租约。技能开始时生成并保存 token，技能自然结束、战斗中断、目标消失或异常退出时释放同一个 token：

```ts
const token = me.attach_effect('rash', sourceToken, duration);
// 技能结束回调
me.detach_effect('rash', token);
```

若调用方不需要手工提前终止，可由租约自身的到期定时器释放；若有多段攻击或 interval，应将 token 放在该动作上下文中，并在所有结束分支走同一个 finally/cleanup 方法。

这样可以正确处理：

- 两个不同状态贡献同一标记；
- 状态与技能临时效果重叠；
- 两个技能临时效果重叠；
- 同一状态的叠层、刷新与替换；
- 批量清除只清状态而保留非状态效果；
- 旧回调晚到，不会清除新效果。

### 4.5 优点

- 对当前共享标记冲突能够做到全来源覆盖；
- 现有读取 `is_busy` 等字段的代码可保持不变；
- 来源之间相互隔离，异步回调顺序不再影响正确性；
- 可以分效果键逐步迁移，并通过禁止新增裸赋值的检查守住边界。

### 4.6 缺点

- `status[]` 管状态生命周期，租约表管效果生命周期，二者仍需成对维护；
- 状态的属性增减、消息和回调仍在 `change_buff()`，共享标记在租约系统，事务边界分散；
- 状态添加成功但租约注册失败，或回调提前返回却未清理 token，都可能产生泄漏；
- 必须一次性找全直接赋值和间接封装路径，才能宣称覆盖完整。

适合希望以可控改动彻底修复当前 bug，但暂时不准备重构整个 buff/技能效果模型时采用。

## 5. 第三档：统一状态与非状态效果生命周期

### 5.1 定位

这一档不再把“buff 状态”和“技能临时字段”视为两个系统。所有具有开始、刷新、叠加、结束或清理语义的效果，都由统一的效果实例管理；是否出现在 `status[]` 和客户端 UI，只是实例的展示策略。

这是需要大改的长期方案，也是唯一能从模型上保证有状态管理和非状态管理效果具有一致生命周期的方案。

### 5.2 统一模型

```text
EffectInstance
  ├─ instanceId：运行时唯一身份
  ├─ source：技能、物品、状态、房间或系统
  ├─ lifetime：开始时间、到期时间、interval、取消条件
  ├─ stacking：独立、叠层、刷新、替换、互斥组、优先级
  ├─ contributions：busy、属性加成、伤害回调等贡献
  ├─ hooks：attach、tick、expire、cancel
  └─ presentation：visible、name、icon、count、客户端信息

EffectRegistry
  ├─ 按 instanceId 管理所有活动实例
  ├─ 按 effectKey 建立贡献索引
  ├─ 统一调度到期和 interval
  └─ 原子提交增删、解析结果与 UI 增量

ResolvedCharacterState
  ├─ busy/faint/rash 等派生结果
  ├─ 属性加成后的派生属性
  └─ 对旧 is_* 字段提供只读兼容访问
```

原来的可见 buff 是 `presentation.visible = true` 的效果实例；连续技期间的自身 rash、短暂 busy 等是 `visible = false` 的内部实例。两者使用相同的 token、定时器、取消和清理规则。

### 5.3 生命周期事务

一次变更应在统一事务中完成：

```text
创建/刷新/取消 EffectInstance
  -> 更新该实例的贡献
  -> 只重算受影响的 effectKey 或属性
  -> 更新 ResolvedCharacterState
  -> 发送一次 UI 增量
  -> 执行约定顺序的 hook
```

定时器只携带 `instanceId` 和可选 `generation/layerId`。刷新实例会增加 generation，旧回调即使晚到也因身份校验失败而成为空操作。

所有结束原因应显式化，例如 `expired`、`dispelled`、`combat_end`、`source_cancelled`、`owner_destroyed`。hook 可以根据原因决定是否显示结束消息，但无论何种原因都走同一资源清理路径。

### 5.4 叠加与互斥策略

将当前 `override` 数字改为明确策略：

- `independent`：每个来源独立存在；
- `stack`：同组增加层数，可选择共享或分层到期；
- `refresh`：刷新同一实例并使旧 generation 失效；
- `replace`：原子取消旧实例并创建新实例；
- `exclusive`：按 priority 选生效者，但保留未生效实例的生命周期；
- `max`：多个贡献同时存在，解析时取最大值。

互斥不通过删除其他实例的声明实现。当前 winner 结束后，解析器自然选出仍有效的下一来源。

### 5.5 查询和性能

不必每次扫描所有实例。可维护 `Map<EffectKey, EffectBucket>`：

- 新增贡献写入 bucket；
- 删除时按 token 失效；
- bucket 缓存解析结果；
- 只有相关 bucket 变化时才重算；
- 贡献很少时使用数组最简单，数量增大后再换最大堆或有序结构。

正确的实例身份和原子生命周期比一开始选择堆结构更重要。当前角色同时持有的控制来源通常很少，先用简单结构更容易验证。

### 5.6 迁移路线

1. 先建立 `EffectInstance`、统一 token 和只读查询 API，同时让旧 `status[]` 通过适配器注册实例；
2. 将 `is_*` 写入改为兼容层告警，迁移所有直接赋值技能为内部实例；
3. 将状态的共享标记、属性贡献、定时器依次迁入 registry；
4. 将客户端状态列表改为 registry 中 `visible` 实例的投影；
5. 移除 `change_buff()` 对生命周期的分散管理和角色字段 setter；
6. 最后将旧 `status[]` 降为兼容视图或完全移除。

迁移期间必须避免新旧系统同时拥有定时器。某个效果一旦迁入 registry，它的到期、刷新和清理就只能由 registry 负责。

### 5.7 优点

- 可见状态和内部效果共享完全相同的生命周期保证；
- 定时器、叠加、刷新、替换、清除、消息和派生字段有统一事务边界；
- 能表达互斥、优先级、分层到期和取消原因，而不篡改其他来源；
- 新效果无需再选择“塞进 status”还是“直接写字段”；
- UI 展示与实际贡献可以区分，同时由同一实例保持一致。

### 5.8 缺点

- 涉及角色状态、技能异步流程、属性贡献、客户端序列化及大量调用方；
- 需要兼容期和严格的迁移清单；
- 若试图一次性替换全部路径，回归风险很高，应按效果键和功能域渐进迁移。

适合作为状态系统的长期架构改造，而不是紧急补丁。

## 6. 建议选择

- 需要尽快修复线上重叠状态：选第一档，同时列出裸赋值为已知限制，并优先把高频裸赋值迁为 internal 状态。
- 要求当前所有 busy/rash 等来源都不再互相误清：选第二档。来源租约是改动量与完整性之间最现实的平衡点。
- 准备继续扩展状态、连续技、房间效果、互斥和分层到期：选第三档，并采用适配器渐进迁移，避免一次性重写。

不建议使用“新 buff 接管字段时删除其他 buff 的标记”。该做法会修改其他实例的声明，却没有结束它们的生命周期；接管者结束后还需恢复旧来源，最终会演变成一套隐式租约或接管栈，复杂度不低于第二档，但更难验证。

## 7. 各档共同的验收用例

至少覆盖以下回归场景：

1. 不同 `id` 的两个 busy 状态按任意顺序结束，较晚结束者始终有效；
2. 同一 `id` 的 `override: 1` 减少一层时，只要仍有层数就不提前失效；
3. `override: 2` 刷新后，旧定时器不能删除新实例；
4. busy、faint、miss、rash、shadow、ig_control 分别验证重叠；
5. `clear_downside()`、`clear_combat_status()`、条件批量清除和全部清除只影响目标来源；
6. interval 提前结束、战斗结束、角色死亡或离开等异常分支不残留贡献；
7. 状态效果与技能内部效果重叠时，任一方结束不清除另一方；
8. 两个技能内部效果重叠时，较早结束者不能清除较晚结束者；
9. 客户端可见状态、服务端派生效果和剩余时间保持一致；
10. 增加静态检查或代码审查规则，禁止新增 `.is_busy =`、`.is_rash =` 等绕过统一入口的写入。

第一档只承诺通过第 1 至第 6 项，并将第 7、8 项作为已知边界；第二档和第三档应通过全部用例。
